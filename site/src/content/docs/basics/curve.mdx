export const rows = [
	{ from: 0, speed: 1.5, spacing: 104 },
	{ from: 256, speed: 2.5, spacing: 80 },
	{ from: 512, speed: 3, spacing: 64 },
	{ from: 768, speed: 3.5, spacing: 56 },
];
export const end = 1024;
export const chartX = (distance) => 150 + distance * 0.21;
export const speedY = (speed) => 70 - speed * 14;
export const gapY = (spacing) => 140 - (spacing - 40) * 0.8;
export const line = (pick, toY) => [...rows, { ...rows[rows.length - 1], from: end }].map((row) => `${chartX(row.from)},${toY(pick(row))}`).join(' ');
export const example = 384;
export const blend = (total) => {
	let i = 0;
	while (i + 1 < rows.length && rows[i + 1].from <= total) { i++; }
	if (i + 1 === rows.length) { return rows[i]; }
	const now = rows[i], next = rows[i + 1];
	const done = (total - now.from) / (next.from - now.from);
	return { from: total, speed: now.speed + (next.speed - now.speed) * done, spacing: Math.trunc(now.spacing + (next.spacing - now.spacing) * done) };
};
export const blended = blend(example);
export const crossing = 64 / 4;
export const framesApart = rows.map((row) => row.spacing / row.speed);
export const barX = (frames) => 80 + frames * 2.6;

## When to use it

When the game should get harder the longer the player lasts: a runner that speeds up, a shooter whose waves get denser, a puzzle game whose pieces fall faster. The start should be easy enough to learn on, and the hardest part should still be possible.

This page grows the [Endless run](/basics/runner/) snippet. The obstacles there already come by distance, so changing the gap between them while running needs no new idea.

## How to think about it

**The difficulty is a table.** Every row says: from this total distance on, this speed and this gap between obstacles. The game looks up the row it's in and uses its numbers. Making the game easier at the start, or harder at the end, means changing numbers in the table, and the loop doesn't change. After the last row there's nothing to look up: the game stays at that row, and that's the hardest the game gets.

**Between two rows, blend them.** Jumping from one row's speed to the next all at once would be a jolt the player feels. Instead, the snippet works out how far the run is between the two rows, from 0 to 1, and takes that much of the way from one row's numbers to the next's. At {example} pixels, halfway from 256 to 512, the speed is halfway from 2.5 to 3, {blended.speed}, and the gap halfway from 80 to 64, {blended.spacing}. The emulator's HUD showed that: at 386 pixels, speed 2.75 and gap 72.

**What the player feels is the time between obstacles.** A gap in pixels means little on its own: 80 pixels at 2.5 pixels a frame is 32 frames to react, and the same 80 at 4 would be 20. Speed and gap work together, so the table should be checked in frames: the gap divided by the speed. The snippet's rows give {framesApart.map((frames) => Math.round(frames)).join(', ')} frames. The hero slides 4 pixels a frame, so crossing from one side lane to the other takes {crossing}. The last row stops exactly there: the hardest the game gets still leaves time for the longest dodge.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `constexpr stage curve[] = { { 0, 1.5, 104 }, ... };` | The table as an array of aggregates, built when compiling. `1.5` turns into a `bn::fixed` there too. |
| `stage difficulty(int total)` | Returns a whole row by value: a small struct, so copying it is cheap and the caller gets both numbers at once. |
| `(next.speed - now.speed) * done / length` | Multiply first, divide after. `done / length` alone would be integer division, 0 until the next row. And `bn::fixed * int` is exact, unlike `bn::fixed * bn::fixed`. |
| `now.speed.round_integer()` | The legs' pace is an `int`. Rounding gives 3 at 2.5, where `integer()` would give 2. |
| `stream.set_precision(3);` | Digits before and after the point together, so the speed prints as `2.75`. |

## Pitfalls

**The game never gets past the start.**
The snippet keeps its distance small with a lap: every 256 pixels it goes back to 0. A test ROM that looked the curve up with that distance, and not the total, showed its speed climbing from 1.50 to 2.44 and dropping back to 1.50 every 256 pixels, for the nine seconds it ran. It never reached the second row. Look up the curve with the total distance, `laps * lap + distance`.

**Past the last row, the game keeps speeding up.**
Blending reads the row after the current one. A test ROM without the snippet's check for the last row blended with whatever came after the table in memory. Past 768 pixels its speed kept going: 4.37 at 961, 12.5 at 2,758, with the gap growing from 56 to 201. Hold the last row: return it as it is, as `difficulty` does.
