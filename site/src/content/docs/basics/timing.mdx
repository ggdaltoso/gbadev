## When to use it

Whenever the frame a key goes down isn't exactly the frame the game wants it. A jump pressed a little before landing should still jump. Two taps on a direction should run, but only when they're close together. A cursor held on a list should step once, then wait, then move by itself. In each case the game keeps a press, or the time of one, for a few frames. Those few frames are a big part of whether controls feel good.

[Input](/basics/input/) is about `pressed`, `held` and `released`. [Combos and sequences](/basics/combos/) keeps a whole history. Here, one counter or one frame number per action is enough.

## How to think about it

**A press can be remembered for a few frames.** `a_pressed()` is true on one frame only. The jump buffer keeps it longer: A sets `jump_buffer` to 8, and every frame in the air takes one off. On the first frame on the ground, if any are left, the hero jumps. A press up to 8 frames early still counts, and a press in the air that's too early is forgotten, as the player would expect.

**The time of a press can be kept, and the next one compared with it.** For the double tap, the snippet keeps the direction last tapped and the frame it was tapped on. When the same direction is tapped again within 15 frames, the hero runs, and it walks again as soon as the direction is let go. A second tap later than that is just a new first tap.

**A held key can repeat, after a pause.** The cursor moves once on the press. Then it counts the frames R or L stays held, and moves again at 20 frames and every 4 after that. The pause is what lets a short tap move one item: without it, a tap a few frames long already repeats. Those two numbers are the same ones a computer keyboard has in its settings.

## The smallest thing that works

The line under the ruler shows the item, what's left of the jump buffer, and whether the hero walks or runs.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `int last_tap_frame = -1000;` | Far in the past, so the very first tap can't be taken as the second half of a double tap. |
| `running = running && step_x != 0;` | Stays `true` only while it was already running and a direction is still held. |
| `bn::min(hero.y() + velocity_y, ground_y)` | The hero never goes below the ground: a fall that would pass it stops on it. |
| `(held_frames - repeat_delay) % repeat_every == 0` | True at 20, 24, 28... `%` is the remainder of the division. |
| `bn::format<48>("Item {}   Buffer {}   {}", ...)` | The whole line is built, compared with the one on screen, and only drawn again when it changed. |

## Pitfalls

**A jump pressed just before landing is lost.**
The same keys went to the snippet and to a test ROM where the buffer lasts one frame, so A only works on the frame it's pressed: a jump, then A again about half a second later, a few frames before landing. The snippet jumped again as it landed. The test ROM landed and stayed on the ground. To the player, that's a jump the game ignored.

**Any two taps run.**
A test ROM with no limit between the taps ran when → was tapped, and then held 1.5 seconds later. A player who walks, stops, and walks the same way again would start running without meaning to. The snippet, with the same keys, walked.

**One tap moves several items.**
A test ROM that repeated with no pause, every 4 frames from the press, moved the marker to item 3 on a single tap of R that lasted 150 milliseconds, about 9 frames. The snippet, with the same tap, stopped on item 1. Picking one item in a long list becomes a fight.
