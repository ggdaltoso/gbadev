## When to use it

When the music should say where the player is: a calm tune in the fields, a busier one in town, something quieter under the trees. Nobody reads a sign that says *Village*, but everyone hears the song change. It works with [a big map](/basics/bigmap/), where there's no door or loading screen to change the music at.

## How to think about it

**A region is a rectangle with a song.** Every frame, the game asks which rectangle the hero is in, and that's the song it wants. The rectangles are checked in order and the first one that holds the hero wins, so the last one can cover the whole map and catch everything else. They don't have to match the art exactly: the forest's trees end in a diagonal, and its rectangle doesn't care.

**One song at a time, so changing songs is a fade out, then a fade in.** `bn::music` plays one module; starting another stops the first. Cutting from one to the other mid-note is jarring, so the snippet lowers the volume of the old song over half a second, starts the new one when it's silent, and raises it over another half second. The song starts from its beginning, which is what you want for a new place.

**Keep apart the song the region wants and the song that's playing.** During a fade they're different: the region already wants the village song, and the fields song is still playing, getting quieter. The snippet keeps `playing` and compares it with the region's song every frame. That also handles a player who steps into the village and straight back out: the region wants the fields song again, it's still the one playing, so the volume just goes back up. Nothing restarts.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `constexpr bn::array<region, 3> regions = { region{ ... }, ... };` | A table of regions built at compile time. Music items are `constexpr` too, so each region can hold its song. |
| `const region& region_at(bn::fixed_point point)` | Returns a reference to an element of `regions`, not a copy. The array lives as long as the program, so the reference never dangles. |
| `return regions.back();` | After the loop, for the compiler: the last region covers the whole map, so the loop always returns first. |
| `if(here.name != shown_name)` | Two `const char*` compared as pointers: each region's name is one string in ROM, so the same region gives the same pointer, and the text is only made again when the region changes. |
| `bn::music_item playing = region_at(hero.position()).song;` | A music item is just a number naming a song, cheap to copy and compare with `!=`. |

## Pitfalls

**Walking back restarts the song.**
Calling `play` whenever the region changes, with a 10-frame visit to the village every 3 seconds, started a song 10 times in 15 seconds of the test ROM, and the fields song was back at its first pattern at the end. With the snippet's rules, in the same test, no song was started again and the fields song had moved on to its second pattern.

**The song never gets past its first notes.**
Calling `play` every frame for the region's song starts it over every frame. After 15 seconds in the test ROM, it was still at its first pattern. Start a song only when it changes.

**A song with more channels than the limit doesn't play.**
Butano gives music 16 channels by default, plus 4 for sound effects, and in maxmod's source the player stops reading a row of the song when it finds a note on a channel past them. With that default, the forest song used 4.1% of the CPU in the test ROM, the same as with no music at all: nothing was being mixed. With the limit raised to 28 in the `Makefile`, it used 21.2%. Check how many channels a module has before using it (The Mod Archive lists it on the module's page), and raise `BN_CFG_AUDIO_MAX_MUSIC_CHANNELS` or pick another song.

**A silent song isn't free.**
At volume 0 the mixer still runs the song. In the test ROM, the CPU used was 9.9% with the village song at full volume, 7.1% at volume 0, and 4.1% with the music stopped. If an area should be silent for a while, `bn::music::stop()` it.
