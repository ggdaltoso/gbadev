## When to use it

When the world is a grid and the player should always be on it: a block-pushing puzzle, a dungeon crawler, a tactics game, an old-school RPG town. Every position is a cell, so the rules stay simple: what's in the cell ahead decides whether the step can happen, and two things are in the same place only if they're in the same cell.

For free movement, pixel by pixel, with collisions against walls, see [Map collision](/basics/collision/).

## How to think about it

**The cell is where the character is; the sprite only follows.** The snippet keeps two positions. The cell, two `int`s, is what every rule reads: walls, and in a real game doors, boxes and enemies. The sprite's position is only for drawing, and every frame it moves toward the cell's center. When a step starts, the cell changes at once, and the sprite takes {framesPerCell} frames to get there. In between, the rules already see the character in the new cell.

**A step starts only when the last one is over.** The buttons are only read on a frame when the sprite is exactly on its cell. On every other frame they're ignored, so a step can't be turned or stopped halfway, and a short tap still makes one whole step. Holding a direction starts the next step on the frame the sprite arrives, so the character walks without stopping: a new cell every {framesPerCell} frames.

**Walls are checked on the cell ahead, before the step.** The level is an array of strings, one character per cell, and a wall is a `#`. When a step would start, the snippet looks at the cell it would go to: if it's a wall, the step never happens. The character never ends up inside a bush, so there's nothing to push it back out of, unlike collisions in free movement. The same array draws the background: the art script reads it out of `main.cpp`.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `constexpr const char* level[] = { "###...", ... };` | An array of pointers to string literals: each row stays in ROM, and `level[y][x]` is the character at column x of row y. |
| `int step_y = step_x == 0 ? ... : 0;` | Sideways wins, and up/down only counts when there's no sideways: diagonals can't happen. |
| `if(hero.position() == target)` | Comparing `bn::fixed` with `==` works here because the sprite only ever moves by whole pixels and stops exactly on the target. |
| `bn::clamp(delta.x(), bn::fixed(-speed), bn::fixed(speed))` | A step of at most `speed` toward the target, that lands exactly on it. See the pitfalls for what happens without it. |
| `(step.x() > 0) - (step.x() < 0)` | The sign of a number, -1, 0 or 1, from two comparisons, since `bool` counts as 0 or 1. Butano has no sign function. |

## Pitfalls

**A tap walks several cells.**
A test ROM that read the buttons on every frame, not only on arrival, moved the cell once per frame while the button was down. A 100 ms tap, six frames, took the cell four cells to the right, up to the bush, and the sprite slid all the way after it, long after the button was up. The snippet, with the same tap, walked one cell. Start a step only when the sprite is on its cell.

**The character stops after one step and shakes.**
16 pixels must be a whole number of moves. A test ROM that moved 3 pixels a frame, without limiting the last move, went 15 pixels, then 18, then back to 15, and so on: one second later its x was still going 37, 40, 37, 39... and it never sat exactly on the cell, so the buttons were never read again. Clamp the last move to what's left, as the snippet does, or pick a speed that divides 16.

**The walk stutters at every cell.**
A test ROM that started a step on one frame and only moved on the next stood still for one frame per cell. Holding right for four cells took 34 frames, against 30 for the snippet: the hero walked, stopped, walked. Start the step and make its first move on the same frame.
