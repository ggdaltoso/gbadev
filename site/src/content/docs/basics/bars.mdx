export const zoom = 4;
export const fills = [8, 8, 8, 8, 8, 8, 6, 0, 0, 0];
export const targetAt = (frame) => (frame < 24 ? 64 : 49);
export const shownSeries = (() => {
	let shown = 80;
	const out = [];
	for (let frame = 0; frame <= 40; frame++) {
		const target = targetAt(frame);
		shown += (target > shown) - (target < shown);
		out.push(shown);
	}
	return out;
})();
export const chartX = (frame) => 40 + frame * 8;
export const chartY = (px) => 16 + (80 - px) * 2.4;

## When to use it

For any number with a top that the player should read at a glance: health, stamina, a boss's life, a charge shot, an oxygen meter, a loading bar. A number in text is exact but has to be read; a bar is read in a blink, and a bar that slides toward its new value shows *how much* just changed.

A bar can also be a few sprites. Drawn with tiles on its own background, as here, it costs no sprites at all, however long it is.

## How to think about it

**A bar is a row of cells, and each cell picks one of nine tiles.** The tileset has a tile for every way an 8x8 cell can be filled: 0 columns, 1, 2... up to 8. To show a fill of some number of pixels, the snippet gives the first cells the full tile, the next one the tile with what's left, and the rest the empty tile. `bn::clamp(filled_pixels - cell * 8, 0, 8)` works that out for every cell at once. With nine tiles, the bar moves one pixel at a time; with only full and empty, it would jump 8 at a time.

**The value and the bar are two numbers, and the bar walks toward the value.** `hp` changes at once when the hero is hit. `shown`, the pixels the bar shows, moves one pixel a frame toward the pixels that `hp` is worth, and stops there. A hit of 7 HP takes 16 frames to drain, so the player sees it go. The rules always read `hp`, never `shown`: the bar is only a picture of it, a little late.

**HP and pixels are different units: scale, multiplying first.** The game counts 37 HP; the bar has 80 pixels. The pixels for some HP are `hp * 80 / 37`, and the order matters: with `int`s, a division throws the fraction away, so dividing first, `hp / 37`, gives 0 for anything less than full, and 0 times 80 is still 0. Multiplying first keeps the big number until the very end, and only the last fraction of a pixel is lost.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `bn::clamp(filled_pixels - cell * 8, 0, 8)` | What's left for this cell after the cells before it took 8 each, kept between 0 and 8. Negative means the fill ended before this cell: empty. |
| `shown += (target > shown) - (target < shown);` | Each comparison is a `bool`, 0 or 1, so the difference is 1, -1 or 0: one pixel toward the target, or none when it's there. |
| `hp = bn::max(hp - 7, 0);` | `bn::max` and `bn::min` keep the HP between 0 and the top. |
| `bar.set_priority(0);` | Priority 0 is drawn in front of everything else: backgrounds and sprites with priority 1 to 3. See the pitfalls for what happens without it. |
| `struct bar_map { ... };` | The map in RAM, as in [A map that changes](/basics/mapedit/): its constructor clears it, draws the ends and fills the bar. |

Art: the bar is drawn pixel by pixel by [`snippets/tools/bars_assets.py`](https://github.com/ggdaltoso/gbadev/blob/main/snippets/tools/bars_assets.py). The garden, from the [Grid-locked movement](/basics/grid/) page, is [Tiny Town](https://www.kenney.nl/assets/tiny-town) by Kenney, and the font, from the [Text and HUD](/basics/hud/) page, is built from [Zelda-like tilesets and sprites](https://opengameart.org/content/zelda-like-tilesets-and-sprites) by ArMM1998. ## Pitfalls

**The bar jumps 8 pixels at a time.**
A test ROM that only had full and empty cells, no partial ones, went from 80 pixels to 72, held there, then went to 64, after a hit of 7 HP. Sampled every 3 frames, the snippet showed 80, 77, 74, 71, 68, 65, 64 over the same frames. One tile per filled width, nine in all, is what makes the bar smooth.

**One hit empties the bar.**
A test ROM that wrote `hp / max_hp * bar_width` drained the bar to nothing after the first hit, at 30 HP of 37. `30 / 37` is 0 with `int`s, so the target was 0 pixels until the HP was full again.

**The bar isn't there.**
A test ROM without `set_priority(0)`, with the bar's background created before the garden's, showed no bar at all: both had the default priority, 3, and the garden, made later, was drawn over it. Created in the other order, it showed, but only by luck. Give the HUD a priority of its own.

**An empty bar on a hero who's still alive.**
A test ROM with 200 HP at the top, and the hero down to 1, showed an empty bar: `1 * 80 / 200` is 0 pixels. With 37 HP, the least the snippet can show is 2 pixels, so it doesn't happen there. With a big top, keep at least one pixel while the HP isn't 0, for example `if(hp > 0) target = bn::max(target, 1);`.
