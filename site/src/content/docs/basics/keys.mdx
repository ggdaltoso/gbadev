## When to use it

When the code has to talk about keys in general instead of one at a time: a controls screen where the player picks which key jumps, a button test in an options menu, a tutorial that shows the key to press, a list of keys a combo is made of. [Input](/basics/input/) asks about one key with a function per key, like `a_pressed()`. Here the key itself is a value that goes in variables, arrays and tables.

## How to think about it

**A key is a value.** `bn::keypad::pressed(key)`, `held(key)` and `released(key)` take a `bn::keypad::key_type`, so the key can come from a variable. With every key in one table, `keys`, each with its name and where it goes on the screen, one loop asks about all of them, lights the ones held, and finds the name of any key. Ten `if`s become one `for`.

**A set of keys is one number.** Each `key_type` is one bit: A is `0x0001`, B is `0x0002`, up to L, `0x0200`. So the keys held right now fit in one `unsigned`, each key OR-ed in with `|=`, and `held & unsigned(key)` asks whether one of them is in it. Comparing that number with the one drawn last is how the snippet knows the screen has to change. The other side: a key's value is a bit, not a position, so it can't be used as an index into an array (see the pitfalls).

**The game asks for actions, and a table turns them into keys.** Game code never says "A": it asks for the key in `bindings` of the action it wants. Remapping is writing another key into that table, and nothing else in the game changes. To remap, the snippet waits for the next key pressed, checking every key in `keys`, and puts it in the table. When that key already belonged to another action, the two swap, so no key does two things and no action is left without a key.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `using key = bn::keypad::key_type;` | A short name for a long type, for this file. |
| `enum class key_type : uint16_t` | In `bn_keypad.h`. An `enum class` doesn't turn into a number by itself, so `unsigned(info.value)` asks for it. |
| `held \|= unsigned(info.value);` | Turns that key's bit on in `held`, leaving the others as they are. |
| `held & unsigned(bindings[action])` | Not 0 when that key's bit is on. As a `bool`, any number but 0 is `true`. |
| `for(key& binding : bindings)` | A reference, so writing `binding` writes into the table. Without `&` it would change a copy. |
| `int x[2] = { -100, -100 };` | Where the next name goes on each line, moved on by `text_generator.width(info.name)`. |

## Pitfalls

**A key used as an index.**
A test ROM that looked names up in a `bn::array` of ten names with `names[int(value)]` stopped on its first frame, on Butano's error screen: "Invalid index: 256". That's R, Dash's key: R's value is the bit `0x0100`, not a position from 0 to 9. A plain C array would have no check, and would read past its end instead. Keep the name next to the key, as in `keys`, and look it up with a loop.

**One key, two actions.**
A test ROM that wrote the new key without the swap let Dash take L while Jump was already on L. Both rows said L, and holding L lit both: one press would jump and dash at once. Give the old key to the action that loses the new one.

<figure style={{ textAlign: 'center' }}>
	<img src="/images/keys/noswap.png" width="480" height="320" style={{ imageRendering: 'pixelated', marginInline: 'auto' }} alt="Jump on L and Dash on L, both lit while L is held." />
	<figcaption>L held, in the test ROM.</figcaption>
</figure>

**The press that opens the wait is taken as the answer.**
A test ROM where **A** opened the wait, and the wait was checked in that same frame, never showed "Press a key". The A that opened it was still `pressed`, so it was the key given: Shoot went straight from B to A, and Jump got B. In the snippet, the wait is checked before START, in an `if` whose `else` reads START, so it starts on the next frame, and START can't be given anyway.
