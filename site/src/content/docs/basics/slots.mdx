## When to use it

When more than one person plays on the same cartridge, or one player wants to keep an old save around: before a boss, or on a second run. [The SRAM page](/basics/saves/) keeps one save at the start of SRAM. Slots are the same idea, several times over, plus a way to know whether each one can be trusted.

## How to think about it

**SRAM is one long row of bytes; a slot is a piece of it.** Give every slot the same struct, and slot *i* starts at *i* times the struct's size. The snippet's slot is 16 bytes, so its three slots are bytes 0 to 47 of the 32 KB, and the rest is free. `bn::sram::write_offset` and `read_offset` copy a struct to and from any offset.

**A slot checks itself.** The format value says *this slot was written by this game*, as on the SRAM page. A slot also ends with a checksum: a number worked out from all the bytes before it, stored with them. Reading the slot back, work it out again. If it matches, the bytes are the ones that were written. So a slot is one of three things: empty (no format), damaged (format, but the checksum doesn't match), or good.

**A save can stop halfway.** SRAM is written a byte at a time. Turn the power off in the middle, and the slot holds the start of the new save and the end of the old one. The format is there, every field holds a sensible value, and the slot is wrong. Only the checksum gives it away. The snippet's **SELECT** does exactly that: it writes the first 8 bytes of a new save and resets the game.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `offsetof(slot_data, checksum)` | The number of bytes before the checksum in the struct, from `<cstddef>`. The checksum covers exactly those, and still does if a field is added before it. |
| `reinterpret_cast<const unsigned char*>(&slot)` | Any object can be read as its bytes through an `unsigned char` pointer. That's what SRAM gets, so that's what the checksum reads. |
| `unsigned sum = 0;` | `sum * 31` overflows after a few bytes. For an `unsigned` that wraps around by definition; for an `int` it's undefined behavior, which the compiler is free to break. |
| `void write_slot(int index, slot_data slot)` | Taken by value: the function fills in the format and checksum on its own copy, and the caller passes a struct with zeros there. |
| `coins_taken \|= 1 << index;` | One bit per coin in a single `int`. `bn::popcount` counts the bits that are set, which is the number of coins. |

## Pitfalls

**A cut save loads as if it were fine.**
Checking only the format, the test ROM read the slot cut in half as *1 coin, 9 seconds*: the time from the new save and the coins from the old one, a moment that never happened. With the checksum, the same bytes read as damaged.

**Saving slot 1 erases slot 2.**
With offsets written by hand, `index * 12`, and a struct that had grown to 16 bytes, the test ROM saved slot 2 and then slot 1, and slot 2 was empty: slot 1's last 4 bytes had landed on slot 2's format. Work the offset out from `sizeof`, so the slots move when the struct grows.

**Every slot is damaged.**
Working the checksum out from `sizeof(slot_data)` includes the checksum field itself, and its value changes as soon as you store the result. In the test ROM a slot read as damaged right after it was saved. Stop at `offsetof(slot_data, checksum)`.

**Reading SRAM every frame isn't a problem.**
In the emulator, reading one 16-byte slot took about 7 timer ticks; a frame is 4389. Reading all three slots every frame would cost half a percent. The snippet reads them once and after each save only because that's when they change.

**A damaged slot is a slot you lose.**
The checksum tells you the slot is bad, but not what was in it. If losing it would hurt, keep two copies of each slot and write them in turns, as the [SRAM page](/basics/saves/#pitfalls) describes: a cut can only damage the copy being written, and the other still holds the save before it.
