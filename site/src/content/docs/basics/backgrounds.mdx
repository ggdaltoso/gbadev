## When to use it

For anything big that's made of repeating pieces: the level, the sky, the frame around a menu. A background covers the whole screen and costs almost nothing to draw or scroll, while covering the same area with sprites would use dozens of them.

This page is about **regular** backgrounds: up to four of them at once, each one a map of 8x8 tiles. The alternatives are affine backgrounds, which can rotate and scale but give up two of the four layers, and bitmap backgrounds, where you draw pixel by pixel at a much higher cost.

## How to think about it

**A background is a map of tiles, not an image.** At build time, Butano cuts the `.bmp` into 8x8 tiles, keeps one copy of each tile (flipped copies count as the same tile), and writes a map saying which tile goes in each cell. Each 256x256 layer below has 1024 cells, but only 25 different tiles in the water and 19 in the land. Repetitive art is cheap; a unique painting is not.

**Maps are 256 or 512 pixels per side.** The hardware draws those directly. Butano also accepts bigger maps, in multiples of 256, and streams the visible part to video memory as you scroll.

**Four layers, stacked by priority.** Each background, and each sprite, has a priority from 0 to 3, and lower numbers are drawn in front. On a tie, sprites go in front of backgrounds. Between two backgrounds with the same priority, `set_z_order` decides, and after that the most recently created one goes in front.

**Palette index 0 is a hole.** Wherever a layer has color 0, you see the layer behind it. Below all layers is the backdrop, the color set with `bn::bg_palettes::set_transparent_color`.

**The position works like a sprite's, and the map wraps around.** `(0, 0)` puts the map's center at the screen's center, and a larger y moves the map down. Past the edge, the hardware starts again from the other side, so a map scrolled by 256 pixels looks exactly like one that didn't move. That makes endless scrolling free: water, clouds, a starfield.

## Pitfalls

**"bpp_mode field not found in graphics json file".**
Sprites guess the bits per pixel from the colors, backgrounds don't. Add `"bpp_mode": "bpp_4"` (up to 16 colors) or `"bpp_mode": "bpp_8"` (up to 256) to the `.json`.

**A background is in front of the wrong thing.**
Two backgrounds with the same priority and z order are ordered by creation, and changing one's priority or z order later counts as creating it again. Don't rely on that: set the priority of every layer explicitly, as the snippet does. And remember that a sprite with the same priority as a background is drawn in front of it.

**One layer hides everything behind it.**
It has no pixels with color 0. Usually the image editor put the "empty" color somewhere else in the palette, so it's drawn as a solid color. Make sure the transparent color is the first one in the palette.

**The colors of one background change when another one appears.**
All 8bpp backgrounds share a single 256-color palette, so two 8bpp layers with different palettes fight over it. Use 4bpp when you can, or export every 8bpp layer with the exact same palette.

**The other side of the map shows up at the edge.**
That's the wrap-around. It's great for water and terrible for a level with borders. When something follows the player, stop it before it shows past the edge of the map (see the camera page, coming soon).

**Map sizes in cells, not pixels.**
`map_item().dimensions()` is measured in 8x8 cells: a 256x256 map is 32x32. Multiply by 8 before comparing with pixel positions.
