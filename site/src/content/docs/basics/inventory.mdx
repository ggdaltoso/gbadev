## When to use it

When the player carries things: potions in an RPG, keys and bombs in an adventure, food here. The items the game knows about are written once, as data. The bag only says which of them the player has, and how many. Adding a new kind of item is a new row, not new code.

It builds on [SRAM saves](/basics/saves/), which keeps the bag, and is a cousin of [Bullet patterns](/math/bullets/) and [A boss in phases](/structure/phases/), which also keep their content in a table.

## How to think about it

**An item is a row of a table. The bag keeps the row's number.** `item_types` has one row per kind of item: its name, how many fit in one slot, and how much it heals. The row's position is the item's id, and it's also the frame of `food.bmp` that draws it. A slot in the bag is just two numbers: which row, and how many. Everything else about the item is looked up when it's needed.

**Adding fills a stack before it takes a new slot.** `add` first looks for a slot with the same item and room left under that item's `stack`. Only if there's none does it take a new slot, and if the bag is full it says no. The food stays on the ground then, and "Bag full" shows: nothing the player found disappears. A test ROM with a bag of two slots, full of candy and a burger, showed it: the pizza stayed under the hero.

**Using an item takes one. An empty slot goes, and the rest move left.** A uses the slot under the cursor: health goes up by the row's `heal`, and the count goes down. At zero, `bag.erase` removes the slot, and every slot after it moves one place left, so the bag never has holes. The cursor can stand on an empty box, so the code checks `selected < bag.size()` before reading the slot.

**The save is plain numbers, written when they change.** `bn::sram::write` copies the bytes of a struct, so `save_data` holds only ints: a format number, the health, how many slots are used, and six `slot`s. That's 15 ints, 60 bytes (worked out, not printed). The game keeps the bag in a `bn::vector` and copies it into the struct on every change. At start it reads the struct back and refills the vector. START restarts the ROM, and the bag comes back as it was.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `constexpr item_type item_types[] = { ... };` | The table, built at compile time and kept in ROM. The `const char*` names point into ROM too. |
| `sizeof(item_types) / sizeof(item_types[0])` | The number of rows, worked out by the compiler, so adding a row needs no other change. |
| `bool add(bn::vector<slot, bag_size>& bag, int item)` | The `&` passes the caller's bag itself, not a copy, so `add` can change it. |
| `bag.erase(bag.begin() + selected)` | Removes one slot and moves the ones after it left. `bag.begin() + selected` points to the slot. |
| `bn::sram::write(save)` | Copies the struct's bytes to SRAM. It only accepts types that can be copied byte by byte (see the pitfalls). |
| `bn::random random;` | Starts from the same state on every boot, so the food appears in the same order every time. For different runs, see [Timers and random numbers](/basics/timers/). |

## Pitfalls

**Using an empty slot stops the game.**
A test ROM without `selected < bag.size()` picked up one candy, moved the cursor to the empty box next to it, and pressed A. It stopped on Butano's error screen: `bn_vector.h`, "Invalid index: 1 - 1", the index asked for and the size. `bn::vector`'s `[]` checks the index with `BN_ASSERT`. A plain array would have read whatever was past the end, without a word (worked out, not tested).

**Without stacking, the bag fills with copies.**
A test ROM whose `add` never looked for a stack put each candy in a new slot. After the same walk as the snippet, it had three slots, candy, burger, candy, where the snippet had two, candy 2 and burger. With six slots, six candies would fill the bag.

**A `bn::vector` can't go into the save.**
A test ROM whose `save_data` held `bn::vector<slot, bag_size> slots` instead of the array didn't build: `static assertion failed: Source is not trivially copyable`, and the same for `Destination`, from `bn_sram.h`. A vector keeps its size and runs code when it's copied, so its bytes alone aren't the vector. That's why the snippet copies the bag into a plain array of `slot`s to save it.
