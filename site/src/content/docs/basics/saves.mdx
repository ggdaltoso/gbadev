## When to use it

For anything that must still be there next time the game is turned on: progress, a high score, options. Everything else the game keeps in memory is gone when the power goes off.

## How to think about it

**SRAM is 32 KB of memory on the cartridge.** A small battery keeps it alive while the GBA is off. `bn::sram::size()` tells you the size, and `bn::sram` has the functions to read and write it. Cartridges can also save to flash or EEPROM, but `bn::sram` only talks to SRAM.

**A save is a struct copied byte by byte.** Put what you want to keep in a struct, and `bn::sram::write(save)` copies its bytes to the start of SRAM. `bn::sram::read(save)` copies them back. Nothing is converted or checked: SRAM has no idea what those bytes mean.

**So you have to recognize your own save.** The first time a game runs, SRAM holds whatever it holds, and `read` hands you that as if it were a save. Keep a known value in the first field. If it's there on start, the save is yours; if not, start a new game.

**Save at moments, not all the time.** At a checkpoint, on a menu option, when a level ends. The player loses what happened since then, and that's the deal every save point makes.

**The emulator needs to know the ROM saves.** Butano puts the text `SRAM_V113` in the ROM, which is how mGBA and other emulators detect the save type. Their `.sav` file is a copy of those 32 KB.

## The smallest thing that works

Walk with the **D-pad**. **A** saves where the hero is, and a coin marks the spot. **START** restarts the game, and the hero comes back to the coin, no matter how far it walked since. **B** erases the save.

## Pitfalls

**The first run starts with nonsense.**
You used what `read` returned without checking it. Compare the format value first, as the snippet does.

**A save from an older build loads wrong.**
You changed the struct, and the old bytes now land in the wrong fields. Change the format value whenever the struct changes. To keep old saves working, keep the old struct too, and when the old format shows up, read it and copy its fields to the new one.

**Your first-run code never runs.**
The emulator keeps the `.sav` next to the ROM, and it outlives every rebuild. Delete it, or erase from the game, to test a new cart.

**"Source is not trivially copyable".**
The struct holds something that manages a resource, like a `bn::sprite_ptr`. Save the numbers you need to create it again. A plain pointer compiles, but what it points to won't be there after a restart, so don't save those either.

**A second value overwrites the first.**
`write` always starts at the beginning of SRAM. Keep everything in one struct, or use `bn::sram::write_offset` with an offset past the first one, like `sizeof(save_data)`.

**The power goes off in the middle of a save.**
Half the bytes are new and half are old, and the format value still looks right. If that would hurt, keep two copies at different offsets, write them in turns, and store a counter and a checksum in each. On start, load the valid copy with the highest counter.

**Saving every frame.**
SRAM is written one byte at a time over a slow 8-bit bus. A struct like this one on a button press is fine; there's no reason to repeat it 60 times per second.

**A destructor was supposed to save.**
`bn::core::reset()` goes back to the start of `main()` without destroying what's alive, so that code never runs. Neither does anything when the player turns the GBA off. Save first, then restart.
