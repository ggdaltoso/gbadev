## When to use it

When one key isn't the whole command. A fighting game's special move is a motion and then a button: down, down-right, right, and A. A cheat code is a sequence typed on the title screen. A soft reset is four keys held together, so it can't happen by accident. They're all the same question asked of the past: did these things happen, in this order, recently enough?

This builds on [Keys as data](/basics/keys/): keys as values, and a set of keys as one number.

## How to think about it

**Keep a short history of what happened, with the frame it happened on.** Each event is a button pressed, or the D-pad turning to a new direction, and the frame number. The D-pad is kept as a direction, not as four keys, so down and right held together are one event, down-right, which no single key could give. The history keeps the last 16 events, and the oldest goes when a new one comes. The snippet shows the last eight at the bottom of the screen.

**A move is what the history has to end with, inside a window.** The fire move is the list `↓ ↘︎ → A`, and the code to turn gold is `L R L R ↑ ↓ A`. Both are checked by `ends_with`, when A is pressed: the last events have to be those, in order, and the first of them can't be more than the window's frames old, 20 for the motion and 180 for the code. Only the end counts, so whatever was pressed before, a wrong key or half a try, doesn't get in the way. The window is what makes a motion a motion: the same keys spread over a second are walking, not a special move.

**A chord is a set held together, and one of its keys pressed just now.** L, R, START and SELECT make one number, `reset_chord`. The four are held when `held & reset_chord` is all of them, in whatever order they went down. The reset also needs one of them `pressed` on this frame: after `bn::core::reset()` the player is often still holding all four, and without that test, the game would reset again on every frame until they let go.

## The smallest thing that works

The top of the screen lists the moves. Do **↓ ↘︎ →** and **A** quickly to shoot. Type **L R L R ↑ ↓ A** to turn the hero gold, and again to turn it back. Hold **L**, **R**, **START** and **SELECT** together to reset: the time goes back to 0. On a keyboard, those are **A**, **S**, **Enter** and **Backspace**.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `bn::span<const unsigned> move` | A view of an array that someone else owns: a pointer and a size. A plain array like `fire` turns into one by itself, so `ends_with(fire, ...)` takes any move. |
| `history.erase(history.begin())` | Moves every event one place down, to make room at the end. With 16 events that's cheap. A ring buffer avoids the moves, if a history gets long. |
| `key(value)` | Turns the number back into a `key_type`, the way `held` and `pressed` want it. |
| `held \|= bn::keypad::held(key(value)) ? value : 0;` | Adds the key's bit when it's held, and nothing when it isn't. |
| `(held & dpad) != direction` | The D-pad changed: a new direction, or let go. Letting go isn't remembered, so ↑ ↑ needs the D-pad let go in between, as typing it does. |
| `hero_palette.set_fade(bn::colors::yellow, ...)` | Mixes the hero's colors with yellow. The palette is the hero's alone, so nothing else turns gold. |

## Pitfalls

**The reset doesn't let go.**
A test ROM that reset when the four keys were held, without asking for a press, stayed on a white screen for as long as they were held, about two and a half seconds in the test, and only started when they were let go. From the code, it reset on every frame: four keys held is true again on the first frame after each reset. In the snippet, with the press, it resets once and runs while the keys are still down. Butano helps here: `bn::core::init()` reads the keys twice, so keys already held when the game starts don't look `pressed` on its first frame.

**A slip breaks the code.**
A test ROM that checked the gold code step by step, going back to the first step on a wrong key, never turned gold when the code was typed after an extra L R: L R L R L R ↑ ↓ A. At the fifth key it expected ↑, got L, and went back to the start, but that L was the start of the real code, and it had been thrown away. The snippet, given the same keys, turned gold: the last seven events are the code.

**Any order of keys over any time is a move.**
A test ROM with no window shot when ↓ and ↘︎ were each held for 0.6 seconds before → and A, about 72 frames for the whole motion. Walking down, then stopping, then walking right and pressing A would shoot too. The snippet, with its 20 frames, didn't shoot with the same keys. How wide the window is is a game design choice: wider is kinder, narrower is harder to do by accident.
