## When to use it

For anything written on screen: score, lives, coordinates, menus, a "Press START". A HUD (heads-up display) is the part that stays put while the game moves under it.

## How to think about it

**Text is sprites.** `bn::sprite_text_generator` draws a string into new sprites, 32 pixels wide each, and puts them in a `bn::vector<bn::sprite_ptr, N>` that you own. The text is on screen while that vector is alive and holds them. There is no "text object" to edit: to change the text, clear the vector and generate again.

**A font is a sprite sheet plus widths.** The sheet has 94 glyphs, 8x8 or 8x16, from `!` to `~` in ASCII order, one below the other, in 16 colors. Without widths, every character takes the full 8 pixels. With a widths table, starting at the space, each character takes its own width, so an `i` doesn't leave a gap.

**Generate when the text changes, not every frame.** Generating copies new tiles to video memory. Once is nothing; 60 times per second for text that didn't change is wasted time. Keep the last value you drew, and compare.

**The HUD has no camera.** Text sprites are created without a camera, so they stay at their screen position while everything that called `set_camera` moves (see [the camera page](/basics/camera/#how-to-think-about-it)).

**Alignment sets what x means.** With `set_left_alignment()`, the default, x is where the text starts. With `set_center_alignment()` it's the middle, and with `set_right_alignment()` the end. y is always the middle of the line. A number whose width changes, like 9 becoming 10 or -1, looks steady right-aligned: its last digit never moves.

**Strings have a fixed size.** There is no heap in a typical Butano game. `bn::string<N>` holds up to N characters, and `bn::format<N>("X {}", value)` builds one, the way you'd use a template string.

## Pitfalls

**The text never shows up.**
The vector holding its sprites was destroyed before the frame was drawn. A vector declared inside an `if`, a loop's body or a helper function dies at its closing brace, and the text goes with it. Declare it where it lives as long as the text should, usually before the loop.

**"output_sprites vector is full".**
The vector's capacity is too small. Each line needs its width divided by 32, rounded up: the hint above is 120 pixels, so 4 sprites. Add every line you put in the same vector.

**The old text stays, or texts pile up.**
`generate` adds sprites to the vector; it doesn't replace them. Call `clear()` first.

**The game slows down, or other sprites flicker.**
You generate text every frame, or keep too many lines alive. Text sprites count toward the 128 the hardware has. Regenerate only when the value changes.

**Accented letters come out wrong or crash the game.**
The font only covers ASCII, `!` to `~`. Anything else, like `ç` or `ã`, needs extra glyphs after the 94 and a `bn::utf8_characters_map` that says where each one is. Butano's `examples/text` does it.

**The text is hidden behind a background.**
Text sprites use the generator's background priority. Call `text_generator.set_bg_priority(0)` before generating so the HUD goes in front of everything.

**The importer rejects the font.**
Fonts must be 4bpp, with tiles that aren't compressed, and the `.json` must say the glyph height (`"height": 16` for 8x16).
