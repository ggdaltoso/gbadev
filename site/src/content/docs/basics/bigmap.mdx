## When to use it

When the world doesn't fit in 512x512 pixels, the biggest map a regular background can have in hardware. A town with its surroundings, an overworld, a long level. You could cut the world into rooms and change rooms at the edges, but if the world should scroll as one piece, a big map is the simple way: you create it like any other background, and the camera does the rest.

## How to think about it

**The whole map stays in ROM; video memory holds the part around the camera.** The snippet's map is 1024x1024, four times what the hardware can show. Butano doesn't try to fit it. It keeps a 256x256 window of the map in video memory, just bigger than the 240x160 screen, starting at the screen's top left corner and moving with it.

**The window is a ring, refilled one column at a time.** Video memory holds 32x32 cells of 8x8 pixels. When the camera moves 8 pixels right, one column of cells leaves the screen on the left and a new one is about to show on the right, so Butano copies the new column of the map into the slot of the one that left. Nothing else moves. The cells are never in order in video memory: the screen starts wherever the ring has got to and wraps around its edges, and the hardware draws it whole because backgrounds wrap anyway.

**A big map is a long list of cells over a short list of tiles.** Each 8x8 cell of the map is 2 bytes that say which tile to draw, from which palette, mirrored or not. The snippet's map has 128x128 cells, 32 KB in ROM. But the tiles themselves are shared: the whole map uses 315 of them, with every repeated grass tile, flipped or not, counted once. A cell has room for a tile number up to 1023, so a regular background can't use more than 1024 tiles, however big its map is. A bigger map is cheap. A map with more different tiles isn't.

Nothing in the code says the map is big. The converter makes it big because it's over 512 pixels on a side, and `world.big()` would return `true`. Changing `world.bmp` for a 256x256 one would run the same code. The only thing that has to follow the map's size is the camera's limit, and it comes from `world.dimensions()`.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `bn::fixed half_width = world.dimensions().width() / 2;` | `dimensions()` is a `bn::size` in whole pixels. Dividing ints and storing the result in a `bn::fixed` converts it once, so every limit below is the same type as a position. |
| `bn::clamp(hero.x() + step_x * speed, -half_width + 8, half_width - 8)` | `bn::clamp` needs three arguments of the same type. `hero.x()` plus an `int` is still a `bn::fixed`, and so are the limits. |
| `int speed = bn::keypad::b_held() ? 4 : 1;` | A value chosen by a condition, in one line. Both sides are `int`, so `speed` is too. |

## Pitfalls

**More than 1024 different tiles won't build.**
A map drawn by hand, where every cell is a little different, runs out of tiles long before it runs out of size. In a test, changing one pixel in 5000 of the snippet's cells made 1177 different tiles, and the build stopped with *Regular BGs with more than 1024 tiles not supported: 1177*. Draw the map from a tileset, so cells repeat.

**The size has to be a multiple of 256.**
A 1000x1000 map stopped the build with *Regular BGs width must be divisible by 256: 1000*. Make the image 1024 wide and fill the rest. Big maps go up to 16384 pixels on a side.

**A compressed big map stops the game.**
With `"compression": "lz77"` in the map's JSON, the test ROM built fine and then stopped at start with *Compressed big maps are not supported*. Butano copies columns straight out of ROM, so the cells have to be there as they are.

**The other side of the map shows at the edge.**
Big maps wrap too. Following the hero without the clamp, the test ROM, with the hero in the top left corner, showed the lake from the right edge of the map on the left of the screen. Clamp the camera, as on [the camera page](/basics/camera/#pitfalls).

**Jumping across the map isn't a problem.**
When the camera moves more than 8 cells in one frame, Butano copies the whole 32x32 ring instead of a column. Measured with `bn::core::last_vblank_usage()`, the test ROM used 2.4% of the V-Blank standing still, 4.0% walking a pixel per frame, 4.3% at 4 pixels, and 29.1% on frames where the camera jumped 600 pixels across and 600 down. Even the jump fits in the V-Blank three times over.
