## When to use it

When the world itself should move: water, lava, torches on a wall, grass in the wind, a conveyor belt. Things that appear many times in a background and never move around. Sprites would cost one each, and there are only 128. Animated tiles cost nothing per copy: change a tile once and every copy on the map changes.

## How to think about it

**Map cells point at tiles, so changing a tile changes every cell that points at it.** A background is a set of 8x8 tiles in video memory and a map of cells, each holding the number of a tile. When the art is imported, identical tiles are stored once, so the 36 waves of the pond only need 8 tiles. `overwrite_tile` copies new pixels over one of them, and every cell with that number shows the new pixels on the next frame:

**The frames are a strip of tiles, and a frame's tile is found by arithmetic.** The frames aren't a background: they're a `regular_bg_tiles` item, a strip of tiles with no map, three 6x6 blocks for the fountain stacked top to bottom. The tile for cell (x, y) of frame `f` is number `(f × 6 + y) × 6 + x`. The code reads which tile a cell of the first fountain points at, and copies the frame's tile over it. The stone rim is the same in every frame, so only 15 of the 36 tiles get copied:

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `const bn::regular_bg_tiles_item& frames;` | A reference member: the struct points at the item in the ROM instead of copying it. A struct with a reference can still be built with braces, as `animations` is. |
| `constexpr tile_animation animations[] = { ... };` | The animations are data, fixed at compile time. Adding a torch is one more line, not more code. |
| `bn::regular_bg_tiles_ptr tiles = plaza.tiles();` | `tiles()` returns a `const` reference, and a `const` object only allows `const` functions. `plaza.tiles().overwrite_tile(...)` doesn't compile: "passing 'const bn::regular_bg_tiles_ptr' as 'this' argument discards qualifiers". The copy shares the same tiles and can change them. |
| `bn::span<const bn::tile> frame_tiles = animation.frames.tiles_ref();` | A view of the frames' tiles in the ROM, indexed like an array, with no copy. |
| `a.data[index] != b.data[index]` | A `bn::tile` is a plain struct of 8 words with no `==`, so `same_tile` compares the words. |
| `(frame + animation.frame_count - 1) % animation.frame_count` | The previous frame, going around: from frame 0 it gives the last one. Adding `frame_count` first keeps the number positive, because `%` of a negative number is negative in C++. |

## Pitfalls

**"There's no space for more overwritten tiles."**
Butano copies at most 32 tiles per frame with `overwrite_tile`. The first version of the snippet copied every cell of the fountain and of one wave, 40 tiles on the same frame, and stopped right away with that error. Skip the tiles that don't change, give animations different speeds so they rarely change on the same frame, or raise the limit with `BN_CFG_BG_BLOCKS_MAX_OVERWRITE_TILES` in the Makefile's `USERFLAGS`.

**Waves cut in half, because the importer stored mirrored tiles once.**
By default, a tile that's another tile mirrored is stored once, and the cell shows it flipped. The wave's right half is its left half mirrored, so both halves pointed at one tile. Each frame, the code copied the left half and then the right half over that same tile, and the waves came out broken (top: the default; bottom: with `"flipped_tiles_reduction": false` in `plaza.json`). The `BN_ASSERT` in `show_frame` stops the game with "Flipped animated cell" instead.

**A copy that's off the 8-pixel grid never moves.**
A copy only shares tiles if it lines up with the 8x8 grid the same way. In a test ROM with the middle fountain at x = 100 instead of 104, all 36 of its cells had tiles of their own: the background went from 49 to 91 tiles, and that fountain didn't change once in 30 captured frames while the other two did. Place copies on multiples of 8 pixels.

**The frames' colors come out wrong.**
A tile stores color numbers, not colors, and those numbers mean whatever the background's palette says. In a test ROM, the fountain's frames were saved with their own palette, in a different order, and the fountains turned white and green. The asset script builds one list of colors and saves the plaza and both strips with it.
