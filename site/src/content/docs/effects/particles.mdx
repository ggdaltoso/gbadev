## When to use it

For effects that are many small things living a short time: sparks when you pick up a coin, dust behind feet, debris from a broken pot, smoke, rain. Each one is too simple and too short-lived to deserve a class with behavior, like [the game objects](/structure/objects/) have. A particle is a sprite and a few numbers.

When the effect is one big animation, like an explosion drawn by an artist, play it as [an animated sprite](/basics/sprites/) instead.

## How to think about it

**A particle is a few numbers picked at random.** Each spark in a burst gets a random angle and a random distance, which together make its way: how far it will fly, and in which direction. The angle goes through `bn::degrees_lut_sin_and_cos`, as on [the vectors page](/math/vectors/). The sparks use their own `bn::random`, so a burst never changes where the next coin appears, the trap from [the timers page](/basics/timers/):

**Where a spark is comes from its age.** A spark doesn't keep a velocity. It keeps where it was born, its way and its age, and each frame works out its place as a tween from [the easing page](/math/easing/): the start plus the way times `ease_out(age / 32)`. So it shoots off and slows down, and lands exactly at the end of its way on frame 32, when it's removed. Every 8 frames, the age also picks a smaller star:

**There's a fixed number of slots, and when they're full, the oldest goes.** The sparks live in a `bn::vector<spark, 48>`. A new burst that doesn't fit erases the first sparks in the vector, the oldest ones, since they're nearly gone anyway. That way pressing **A** always shows a full burst, and the game never asks for more sprites than you planned for:

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `void burst(bn::ivector<spark>& sparks, ...)` | `bn::vector<spark, 48>` and `bn::vector<spark, 100>` are different types. Both are a `bn::ivector<spark>`, so a function that takes that works with any capacity. |
| `auto [sin, cos] = bn::degrees_lut_sin_and_cos(...)` | The function returns a pair, and a structured binding names both halves at once. The order is sine, then cosine. |
| `sparks.erase(sparks.begin())` | Removes the first element and slides the rest down, so the vector stays in age order and the front is always the oldest. |
| `constexpr int spark_frames = frames_per_graphic * 4;` | One constant made from another. Change how long a frame lasts, and the lifetime follows. |
| `particle.age % frames_per_graphic == 0` | True once every 8 frames, which is when the star gets smaller. |

## Pitfalls

**`set_tiles` on every frame.**
It's tempting to set each spark's frame every frame, since the age says which one it is. The test ROM measured 48 sparks: calling `set_tiles` on all of them every frame, with the frame they already had, used 15.87% of the frame, against 6.69% for moving them all. With a new frame every time, 24.02%. Call it only when the frame changes, as the snippet does:

**A big burst costs its frame.**
Making a sprite isn't free either. Creating 48 sparks in one frame used 43.82% of that frame, and destroying them 15.19%. A burst on a frame that's already busy can push it over. Keep bursts small, 12 or 24 here, or spread a big one over a few frames.

**"Invalid graphics index: 4 - 4".**
Without `particle.age < spark_frames`, the spark asks for frame 32 / 8 = 4 on its last frame, and the spark has frames 0 to 3. The game stops with that error from `bn_sprite_tiles_item.h`. The test in the snippet keeps the index in range.

**"No more sprite items available".**
The 129th sprite stops the game with that error from `bn_sprites_manager.cpp`, as a test ROM making 130 sparks showed. The vector's capacity is your promise to stay under it, and the hero, the coins and the text count too. If you'd rather drop a spark than stop, `bn::sprite_ptr::create_optional` returns an empty `bn::optional` when no sprite is left.

**Scaled or rotated sparks vanish.**
The hardware only has time to draw so many sprite pixels on each line of the screen, and a scaled or rotated sprite costs much more than a plain one. In a test ROM, 30 plain sparks on one line all showed. 30 sparks scaled to 1.5 on another line showed 27: the first 3 were missing. Keep sparks plain, or few on any one line.
