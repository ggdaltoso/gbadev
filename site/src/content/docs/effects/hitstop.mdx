## When to use it

When a hit should feel like it landed: a sword striking an enemy, a punch, a hammer on a rock. For a fraction of a second everything stops, as if the blow met resistance, and then the game goes on. Fighting games and action games use it on nearly every hit, from about 3 frames for a light one to 10 or more for a heavy one.

## How to think about it

**The world stops, the hit doesn't.** During hitstop the hero stays in the pose with the sword out and the target stops its own animation. But the spark of the impact keeps playing, because it *is* the hit, and the game still reads the buttons and draws the HUD. Freezing everything, input included, feels like the game hitched, not like a heavy blow.

**Hitstop is a counter that skips the world.** A hit sets `freeze` to 6. Every frame, if it's above 0, the game counts it down and skips the part of the loop that moves the world. Everything still goes through `bn::core::update()`, so the screen keeps being drawn: it just shows the same pose. Nothing in the world needs to know about the hitstop, because nothing in the world runs.

**It makes the swing longer, and that's the point.** The swing is 4 poses of 4 frames. Without hitstop, the sword is out for 4 frames, 67 milliseconds, too short to read. With 6 frames of hitstop on the first frame of that pose, the sword stays out for 10, and the whole swing takes 22 frames instead of 16. The spark starts on the hit and keeps animating, so it plays across the freeze.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `constexpr int swing_frames = frames_per_pose * 4;` | Constants built from other constants. Change the speed of the swing in one place and the hit frame follows. |
| `if(++swing == swing_frames)` | `++swing` adds one first and gives the new value, so the swing ends on its last frame. `swing++` would give the old one and end a frame late. |
| `bn::optional<bn::sprite_animate_action<4>> spark_flash;` | An animation that exists only while it plays. `reset()` throws it away, and `if(spark_flash)` asks whether there is one. |
| `void show_text(..., bn::vector<bn::sprite_ptr, 16>& sprites, ...)` | The vector of text sprites is passed by reference, so the function fills the caller's own vector and the text stays on screen. |
| `hitstop_on ? "A: swing   B: hitstop on" : "..."` | Two string literals of different lengths: `?:` turns both into a `const char*`, and `generate` takes that as a `bn::string_view`. |

## Pitfalls

**One swing, four hits.**
Checking for the hit on every frame of pose 2, instead of on its first frame, hit again as soon as each stop ended: the sword was still out. In the test ROM a single swing hit 4 times and the world was frozen for 24 frames. Check once per swing, or remember that this swing already hit.

**Presses during the stop are lost.**
`bn::keypad::a_pressed()` is true for one frame only. A version that read it only when the hero was free to swing dropped a second press made 200 milliseconds after the first: one swing in the test ROM, against two in the snippet. The snippet reads the buttons every frame and keeps `wants_swing` until the hero can use it.

**Two hits add up.**
With two logs in reach, `freeze += 6` froze the test ROM for 12 frames on one swing. Each extra target makes the stop longer, and a crowd turns one swing into a pause. The snippet sets `freeze = 6`, so a second hit on the same frame leaves it at 6.

**Waiting inside the loop freezes the spark too.**
Calling `bn::core::update()` 6 times in a row at the hit, instead of counting down, does stop the world. But nothing else runs either: in the test ROM the spark stayed on its first frame for the whole stop and only played afterwards, and no button could be read in between.
