export const circle = { x: 150, y: 70, r: 52 };
export const lineStep = 8;
export const lines = Array.from({ length: Math.floor((2 * circle.r) / lineStep) + 1 }, (_, i) => {
	const dy = -circle.r + i * lineStep;
	const half = Math.sqrt(Math.max(0, circle.r * circle.r - dy * dy));
	return { y: circle.y + dy, left: circle.x - half, right: circle.x + half };
});
export const stepLabels = ['open: the hero steps on the hole', 'closing', 'closing', 'swapped, opening', 'open again'];

## When to use it

When the hero goes from one place to another: through a door, down a hole, into a house. The circle closing on the hero says *this is where you were*, and opening on them says *this is where you are*. [The mosaic page](/effects/mosaic/) has a teleport that dissolves the picture, and [the scenes page](/structure/scenes/) fades to black. The iris is a third way, and the way the transition is built is the same for all three.

## How to think about it

**A circle is a window, one line at a time.** A rectangle window has a left, a right, a top and a bottom. The GBA draws the screen line by line, so an [H-Blank effect](/effects/hblank/) can give the window a different left and right on each of the 160 lines. Make each line as wide as the circle is at that height, and the window is a circle. Inside it everything shows; outside it nothing does, and the black backdrop shows through.

**The transition is a state, not a function.** It takes 48 frames, and the game keeps running through them: the loop draws every frame, and the iris changes a little each time. So the game is in one of three phases. *Open*: the hero walks. *Closing*: the circle shrinks over 24 frames and input waits. When it's closed, the screen is black, and that's the moment to change places: hide one background, show the other, move the hero. *Opening*: the circle grows back on the new place.

**The circle starts just big enough.** At its largest, the circle only has to cover the screen corner furthest from the hero. With the hero by the hole at (56, -36), that's a radius of 211. Starting from a round 300 instead, it would take 7 of the 24 frames to shrink below 211, and for those 7 nothing on screen would change, worked out from the snippet's numbers. `covering_radius` works out the smallest one each time.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `using window_lines = bn::array<bn::pair<bn::fixed, bn::fixed>, bn::display::height()>;` | A short name for a long type. The size comes from the screen, so it can't be off by one. |
| `enum class iris_phase { open, closing, opening };` | The three phases by name. An `enum class` won't mix with plain numbers by accident. |
| `void shape_iris(window_lines& lines, ...)` | The array is changed in place, by reference. The H-Blank effect keeps reading this same array, so copying it would draw nothing new. |
| `constexpr bn::fixed_point outside_hole(56, -24);` | A point built at compile time. The hole's sprite and the arrival spot come from the same constant. |
| `phase == iris_phase::closing ? full * (iris_frames - frame) / iris_frames : full * frame / iris_frames` | One expression for both directions. Multiplying before dividing keeps the steps even with `int`: `frame / iris_frames` alone would be 0 until the last frame. |

## Pitfalls

**The circle never shows, and the place just changes.**
The H-Blank effect read the array once, when it was created. Without `reload_deltas_ref()` after each change, the test ROM kept the full-screen window through the whole transition, and after 24 frames the grass turned into the cave at once. The effect keeps a reference to your array, and only reads it again when you tell it to.

**Arriving on the way back.**
Putting the hero right on the other hole sends them back at once. In the test ROM, with the hero arriving with their feet on the hole, the game went back and forth between the grass and the cave by itself, a round about every 48 frames, with no button pressed. The snippet puts the hero 20 pixels above the hole, so they have to step onto it.

**Input that doesn't wait.**
Checking the hole every frame, during the transition too, restarted the closing on every frame the hero stood on it. In the test ROM the iris got one frame in, a black corner at the bottom left, and stayed there. Only the open phase reads the D-pad and checks the hole.

**Past the screen's sides isn't a problem.**
The window's hardware registers only go from 0 to 255, so a left edge at -150 looks like trouble. The first version of the snippet clamped every line to the screen, just in case. Without the clamp, the test ROM's circle shrank evenly frame after frame: Butano clamps the values itself, in `bn_display_manager.cpp`. One less thing to write.
