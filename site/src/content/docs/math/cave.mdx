## When to use it

When a game wants places nobody drew by hand: a new cave every run in a roguelike, a mine that's different on each visit, a level you can share by telling a friend its number. On the GBA there's no room to store hundreds of maps, but there's room for a little code and one number per map.

## How to think about it

**Start from noise, then smooth it.** First every cell is rock or floor at random, 45% rock, like static on a TV. Then a pass looks at every cell's 8 neighbors and lets the majority win. Single rocks in the open disappear, lone holes in the rock fill in, and after a few passes what's left are rounded caves.

**The rule counts neighbors.** More than 4 of the 8 are rock: the cell becomes rock. Fewer than 4: floor. Exactly 4: it stays as it was. Cells outside the grid count as rock, so the cave closes at the edges. Every cell decides from the grid as it was before the pass, so the pass reads one grid and writes another.

**A seed is where the counting starts.** `bn::seed_random` keeps a counter: each number it gives is the counter, plus one, scrambled. So the same seed always gives the same numbers in the same order, and the same cave. But the next seed starts one count later, and gives the same numbers shifted by one. A cave reads 504 numbers, one per cell inside the edge, so the snippet spaces the seeds 1024 counts apart and no two caves share a number.

## The smallest thing that works

The snippet shows seed 1 being smoothed, one pass every 20 frames. **A** goes to the next seed and **B** back to the one before, which comes out exactly as it was. The cave is written into a background map that lives in RAM, and `reload_cells_ref` sends it to the screen after each change.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `struct cave { bool rock[rows][columns]; };` | A plain array can't be copied with `=`, but a struct that holds one can. The 600 cells become one value with a name. |
| `cave caves[2];` and `current = 1 - current;` | The two grids swap roles by index: the one just written becomes the one read next. Nothing is copied. |
| `smooth(const cave& from, cave& to)` | `const` says which grid is only read, and the compiler stops `smooth` from writing to it. It doesn't stop a caller passing the same cave twice: that's the in-place pitfall below. |
| `edge \|\| random.get_int(100) < rock_percent` | `\|\|` stops at the first `true`, so edge cells draw no number. Changing which cells are edges shifts the numbers for every cell after them. |
| `bn::unique_ptr<cave_map> map(new cave_map());` | The map's 1024 cells live on the heap, as in Butano's own example, and are freed when `map` goes away. |
| `bn::regular_bg_map_cell_info info;` | A cell is 16 bits holding the tile number, two flips and a palette. The info object sets the parts by name and gives back the cell. |

## Pitfalls

**The next seed is the same cave, one cell over.**
The first version passed the seed to `bn::seed_random` as it was. Seeds 1, 2 and 3 all came out as one cave in slightly different places. In the test ROM, the noise of seed 2 matched the noise of seed 1 shifted by one cell in all 503 cells it could compare. With the seeds 1024 apart, as in the snippet, it matched in 261, which is chance.

**Smoothing the grid in place.**
Writing each cell back into the grid being read means the cells after it see its new value, not the old one. Over the first 20 seeds, the test ROM found 142 cells different on average out of 600, and rock went from 335 cells to 402. The change sweeps across the grid in the order of the loops, top to bottom and left to right.

**Pockets you can't reach.**
Nothing in the rule keeps the cave in one piece. Of the first 20 seeds, 13 had floor cut off from the rest, up to 4 separate areas, and 819 of their 5294 floor cells were outside the biggest one, 15%. Seed 11 lost 115 cells that way, and seed 1, in the demo, is in 3 pieces. Before putting a hero and an exit in a cave, [flood fill](https://en.wikipedia.org/wiki/Flood_fill) from one floor cell and fill in, or connect, whatever it doesn't reach.

**It takes several frames.**
Timed in the test ROM, the noise took 2109 timer ticks, one pass 7613, and writing the map 928, against 4389 in a frame. One pass alone is 1.7 frames, and the whole cave about 7.6. The snippet spreads the passes out to show them, so each one costs a dropped frame. A game would build the cave while the screen is dark, between two scenes.
