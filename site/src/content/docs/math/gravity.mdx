export const physics = { gravity: 0.25, jump: -5, cut: -1.5, maxFall: 4 };
export const simulate = (holdFrames) => { const points = [{ frame: 0, height: 0, speed: 0 }]; let speed = physics.jump; let height = 0; for (let frame = 1; frame < 80; frame++) { if (frame > holdFrames && speed < physics.cut) speed = physics.cut; speed = Math.min(speed + physics.gravity, physics.maxFall); height -= speed; if (height <= 0) { points.push({ frame, height: 0, speed }); break; } points.push({ frame, height, speed }); } return points; };
export const held = simulate(99);
export const tapped = simulate(4);
export const apex = Math.max(...held.map((p) => p.height));
export const tapApex = Math.max(...tapped.map((p) => p.height));
export const arcX = (frame) => 30 + frame * 8;
export const arcY = (height) => 140 - height * 2.4;
export const fall = Array.from({ length: 28 }, (_, i) => ({ frame: i + 1, capped: Math.min((i + 1) * physics.gravity, physics.maxFall), free: (i + 1) * physics.gravity }));
export const fallX = (frame) => 40 + frame * 11;
export const fallY = (speed) => 140 - speed * 15;

## When to use it

For anything seen from the side that falls and jumps: the hero of a platformer, a ball, an enemy that hops, coins that pop out of a block. Gravity is what makes a jump an arc instead of a lift going up and down.

It builds on [Velocity and acceleration](/math/velocity/): there the velocity is horizontal and changes when you press the D-pad; here the vertical velocity changes every frame on its own. A game seen from above has no gravity pulling things down the screen.

## How to think about it

**Gravity changes the velocity, and the velocity changes the position.** The character keeps a vertical velocity between frames. Every frame, gravity adds 0.25 to it, and the velocity is added to the position. A jump is nothing but a negative velocity: -5 sends the character up, gravity slows the rise by 0.25 each frame, and after 20 frames it's going down. Nothing in the code says "arc": the arc comes out of those two additions.

**A fall has a top speed.** Left alone, gravity would make a fall faster and faster: after a long drop the character would cross a whole platform in one frame, and the player couldn't follow it. The snippet stops the velocity at 4 pixels per frame. Falling from rest, it gets there after 16 frames, and from then on the fall is a steady 4 pixels per frame.

**Letting go of A cuts the jump short.** Every jump starts at the same speed. While A is held, gravity alone slows the rise. Once A is up, the snippet won't let the character rise faster than 1.5 pixels per frame, so it stops climbing a few frames later. A tap gives a hop, a long press the whole jump, and the player controls the height without thinking about it. The cut only lowers a rising speed, so letting go on the way down changes nothing.

**Landing is crossing a platform's top.** Each frame, the snippet takes where the feet were and where they'd be after moving. If they were above a platform's top and would be on it or below, they land: the feet go exactly on the top, and the velocity goes to 0. The test only runs while falling, so the character jumps up through a platform from below and lands on it on the way down, like the one-way platforms of many platformers. Whether it's standing is worked out again every frame: walking off the edge, nothing is under it any more, and it falls.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `constexpr bn::fixed gravity = 0.25;` | The conversion from `0.25` happens when compiling. A quarter is exact in `bn::fixed`, which keeps 12 bits after the point; see [Fixed-point numbers](/math/fixed/). |
| `bn::min(velocity_y + gravity, max_fall_speed)` | Speeds up and caps in one line. Both sides are `bn::fixed`, so `bn::min` knows which type to return. |
| `constexpr platform platforms[] = { { -120, 120, 44 }, ... };` | An array of aggregates, filled when compiling. The size comes from the number of entries. |
| `for(const platform& under : platforms)` | A range-for works on a plain array too: the compiler knows its size. |
| `stream.set_precision(4);` | `bn::ostringstream` writes a `bn::fixed` with this many digits in total, before and after the point. The default prints `21.25000`; 3 would cut it to `21.2`. |
| `player.set_horizontal_flip(direction > 0);` | The character faces left in the pack, so walking right is the flipped one. Check which way your art faces before choosing the sign. |
| `walk_frames / 8 % 2` | Integer division first, then the remainder: a frame number that flips between 0 and 1 every 8 frames. |

## Pitfalls

**The character walks off a ledge and stays in the air.**
A common first version sets "on the ground" when landing and clears it when jumping, and only applies gravity in the air. In a test ROM written that way, the character walked off the right edge of the top platform and kept walking at the same height, with nothing under it. Walking off an edge never clears the flag. Work out whether it's standing every frame, from what's under its feet, as the snippet does.

**Pressing A in the air jumps again.**
Without the `on_ground` check, every press sets the velocity back to -5. In a test ROM, each press in the air raised the character about 12 pixels, and after 9 presses in a row its head was at the top of the play area. A double jump is a design choice: if you want one, count the jumps in the air and reset the count on landing.

**The character sinks into the ground and falls through it.**
A test ROM landed the character whenever its feet were inside a platform's 18 pixels, setting the velocity to 0 but leaving the feet where they were. Gravity then added 0.25 every frame and the velocity was zeroed again, so the feet went a quarter of a pixel deeper each frame: the top of the screen read 15.5 pixels into the grass, then 17.7, and then the character dropped out of the screen. Put the feet on the top when landing.
