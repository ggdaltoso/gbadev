export const rows = [...mazeHeader.matchAll(/"([#.]+)",/g)].map((match) => match[1]);
export const steps = [[1, 0], [-1, 0], [0, 1], [0, -1]];
export const search = (goal) => {
	const distance = rows.map((row) => [...row].map(() => -1));
	const queue = [goal];
	distance[goal[1]][goal[0]] = 0;
	for (let next = 0; next < queue.length; next++) {
		const [x, y] = queue[next];
		for (const [dx, dy] of steps) {
			if (rows[y + dy][x + dx] === '.' && distance[y + dy][x + dx] < 0) {
				distance[y + dy][x + dx] = distance[y][x] + 1;
				queue.push([x + dx, y + dy]);
			}
		}
	}
	return { distance, queue };
};
export const goal = [13, 8];
export const found = search(goal);
export const trail = (start) => {
	const cells = [start];
	let [x, y] = start;
	while (found.distance[y][x] > 0) {
		const [dx, dy] = steps.find(([dx, dy]) => found.distance[y + dy][x + dx] === found.distance[y][x] - 1);
		x += dx;
		y += dy;
		cells.push([x, y]);
	}
	return cells;
};
export const size = 20;
export const cx = (x) => 10 + x * size + size / 2;
export const cy = (y) => 10 + y * size + size / 2;
export const cells = rows.flatMap((row, y) => [...row].map((c, x) => ({ x, y, crate: c === '#' })));
export const ring = 4;
export const startA = [1, 1];
export const startB = [3, 7];

## When to use it

When something has to find its way through walls: a hint that shows the player the way to the next goal, a cursor that says how many steps away a spot is, or anything that must reach a place without walking into a dead end. Going straight toward the goal fails as soon as a wall is in the way; a search finds the way around.

## How to think about it

**A breadth-first search is a wave that leaves the goal.** The goal is at distance 0. Its floor neighbors are at 1, their new neighbors at 2, and so on, ring after ring, until every floor cell has a number. A queue keeps the rings in order: a cell joins at the back when it gets its number, and cells are taken from the front. Every cell at distance 1 joins before any at 2, so the first time the wave reaches a cell is by a shortest way, and its number never has to change.

**Search from the goal, not from the hero.** A search from the goal gives every floor cell its number of steps to the goal: one map that answers every start. The hero can walk anywhere, take a wrong turn, come back, and the map stays right, because only the goal decides it. The snippet searches once when the coin moves, and never while the hero walks.

**The way to the goal is downhill.** From any cell, one of its neighbors is exactly one step closer: its number is one less. Step there, and repeat until 0. That's the trail of dots the snippet draws, and it costs only as many steps as the trail is long. When two neighbors are both one less, both ways are shortest; the snippet takes the first one in its list of steps.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `using distance_map = bn::array<bn::array<int, maze::columns>, maze::rows>;` | A name for an array of rows, each an array of columns, so it's read `distance[row][column]`, like `maze::cells`. |
| `int& at(distance_map& distance, bn::point cell)` | Returns a reference to the number in the map, not a copy, so `at(distance, goal) = 0` writes into the map. |
| `for(int next = 0; next < queue.size(); ++next)` | An index, not a range-based `for`: a range-based `for` reads the end once, before the first cell, and would stop before the cells pushed during the loop. |
| `row.fill(-1);` | Every cell starts unknown. A crate is never reached, so it stays -1. |
| `while(at(distance, cell) > 1 && ! dots.full())` | Stops one step before the coin, so no dot covers it. And the vector can't overflow, however long the trail. |
| `trail_from = bn::point(-1, -1);` | A cell that can't exist, so the next frame's `here != trail_from` is true and the trail is drawn again on the new map. |

## Pitfalls

**Marking a cell when it leaves the queue.**
If a cell gets its number when it's taken from the queue instead of when it joins, a cell can join several times before it's taken: once from each neighbor that reaches it. The numbers come out the same, but the queue grows. In the test ROM, the maze queued 66 cells for 63 floor cells, and an open 13x8 room queued 188 for 104. With the snippet's queue, room for 150 cells, the open room stopped on Butano's error screen: *Vector is full*.

**Searching every frame.**
One search of this maze took 462 timer ticks in the test ROM, and a frame is about 4389: a tenth of the frame. The open room took 846, almost a fifth. A search costs more with every floor cell, so run it when the goal or the walls change, not every frame.

**The hero's cell from the sprite's center.**
The hero sprite is 32x32 and its feet are 10 pixels below its center. At the snippet's start, the center is in the row of crates above the hero: the test ROM read a distance of -1 there, so the trail loop, which runs while the distance is more than 1, would draw no dot at all. The snippet takes the cell under the hero's feet, the same point its collision uses.
