export const smoothstep = (t) => t * t * (3 - 2 * t);

## When to use it

When something must get to a point in a set time: a coin flying to the counter, a menu sliding in, a camera panning to a door, a title dropping into place. You know where it starts, where it ends and how many frames it takes, and you work out every frame in between. When the movement depends on the player, or should react to things on the way, use [a velocity](/math/velocity/) instead.

Butano does the plain, even version for you: `bn::sprite_move_to_action`, `bn::bg_palettes_fade_to_action` and the other `*_to_action` classes. This page builds it by hand, because that's how you get the curves.

## How to think about it

**A point on the way is a fraction of the way.** Take the way from the start to the end, `to - from`, multiply it by a fraction `t`, and add it to the start. `t = 0` gives the start, `t = 1` gives the end, and `t = 0.5` the middle. That's `lerp`, short for linear interpolation:

**Time and progress are two different fractions.** The flight takes 40 frames, so after `frame` frames, the time gone is `frame / 40`. An easing curve turns that into how far along the coin is. Linear gives back the same number. Ease out runs ahead early and slows down at the end. Smoothstep starts slow, speeds up in the middle and slows down again. All three start at 0 and end at 1, so the flight always takes 40 frames:

**The end is a frame count.** The flight is over when `frame` reaches 40. Then `t` is 40 / 40, exactly 1, every curve gives exactly 1, and `lerp` gives exactly the counter. Nothing is compared against a position, so there's no "close enough" to get wrong.

## The smallest thing that works

The **D-pad** walks the hero. Touch a coin, and a copy flies to the counter in the corner in 40 frames, while the coin on the map jumps somewhere else. The counter goes up when the copy gets there. **A** picks the curve for the next coins: linear, ease out or smoothstep. The hitboxes are the tight ones from [the hitboxes page](/math/hitboxes/).

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `using easing = bn::fixed(*)(bn::fixed);` | A name for the type "pointer to a function that takes a `bn::fixed` and returns one". `linear`, `ease_out` and `smoothstep` all fit it. |
| `constexpr curve curves[] = { { "Linear", linear }, ... };` | A function's name, without `()`, is a pointer to it. The array pairs each curve with its label, so picking a curve is picking an index. |
| `coin.function(t)` | Calls whatever function the pointer holds. Each flight keeps the curve it started with, even after **A** changes it. |
| `flight{ flying, coin.position(), curves[curve_index].function }` | Fills the fields in order. `frame` is left out, so it takes its default, `= 0`, from the struct. |
| `int arrived = bn::erase_if(...)` | `bn::erase_if` returns how many it removed: here, how many coins got to the counter this frame. |

## Pitfalls

**The coin stutters.**
`(to - from) * t` with `bn::fixed`'s `*` drops 6 bits from each side before multiplying, so `t` only has 64 steps between 0 and 1. On a 204-pixel flight in 40 frames, the test ROM moved the coin 3, 7, 3, 6, 6, 4, 6, 3 and 7 pixels on the first frames, where it should move about 5 each time. `safe_multiplication` keeps every bit, as `lerp` in the snippet does:

**The coin stops short, or goes past.**
Adding `1 / 40` to `t` every frame looks the same as `frame / 40`, but `1 / 40` isn't exact in `bn::fixed`: it's 102 4096ths instead of 102.4. After 40 frames `t` was 4080 4096ths, and the coin stopped 0.8 pixels short of -104. Waiting for `t >= 1` instead took 41 frames and went 4.3 pixels past. Keep the frame count and divide it each time.

**The coin never quite gets there.**
`position += (target - position) / 8` is the popular one-line ease out, and it looks right: the coin was within half a pixel after 46 frames. But it never lands: after 91 frames the step rounded to 0 with the coin still 7 4096ths away, so `position == target` is never true. With `* 0.125` it froze after 76 frames, 56 4096ths away. If something has to happen on arrival, use a frame count.

**The coin waits, then jumps.**
`frame / flight_frames` with two `int`s is 0 until the last frame and 1 on it: the test ROM printed 0 for frame 39 and 1 for frame 40. The coin sits still for 39 frames and teleports. Turn one side into a `bn::fixed` first, as the snippet does with `bn::fixed(coin.frame) / flight_frames`.

**"Action is done".**
Calling `update()` on a `bn::sprite_move_to_action` after its last frame stops the game with that error from `bn_value_template_actions.h`. Check `done()` first, or drop the action when it's done, the way the snippet drops finished flights. Butano's actions don't stop short either: on the last frame they set the final value instead of adding one more step.
