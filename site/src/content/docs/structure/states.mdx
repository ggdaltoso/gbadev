## When to use it

When something behaves differently depending on what it's doing: an enemy that patrols, then chases, then gives up; a door that's closed, opening, open; a player that can be walking, jumping or hurt. The sign you need one is a pile of `bool`s, like `is_chasing` and `is_returning`, that should never be true together but sometimes are.

## How to think about it

**One value says what it's doing.** An `enum class` lists every state, and a single variable holds the current one. It can't be in two states at once, because a variable holds one value.

**Each state only asks "do I stay or go?".** In the `switch`, each `case` does what that state does every frame, then checks the conditions to leave it. It doesn't need to know about the other states, only their names.

**Changing state happens in one place.** `_enter` sets the new state and does what should happen once, on the way in: reset the timer, start an animation. Every transition goes through it, so none of them forgets a step.

**The diagram is the design.** Draw the states as boxes and the conditions as arrows before writing code. If an arrow is missing, the code will be too.

Some of the C++ that helps:

| In the code | Why |
|---|---|
| `enum class log_state` | The names live inside the type: `log_state::CHASE`, not just `CHASE`, so they don't clash with anything else. And it doesn't turn into an `int` by accident. |
| `static_cast<int>(_state)` | Turns it into a number on purpose, here to pick its name from `state_names`. |
| `default: BN_ERROR(...)` | A state with no `case` stops the game with a message, instead of the log doing nothing. |
| `[[nodiscard]] bool near(...)` | A free function: it doesn't need a log, so it isn't part of the class. |

## Pitfalls

**"this statement may fall through".**
A `case` without `break` runs into the next one. Without the `break` after `ALERT`, every frame of the pause also runs the code of `CHASE`, so the log moves and can give up before it was supposed to start. The compiler warns, so read the warnings.

**The animation is stuck on its first frame.**
The animation is created inside the `case`, so it starts over every frame and never gets to frame two. Testing it, the index was still 0 after a second of chasing. Start animations in `_enter`, once.

**A new state does nothing, and the compiler says nothing.**
With a `default`, the compiler stops warning about states with no `case`. Without one, you'd get "enumeration value 'STUNNED' not handled in switch", but also Butano's `-Wswitch-default` warning. The `BN_ERROR` in `default` is how you find it here, the first time the state is used.

**The state changes, but the timer doesn't reset.**
Something set `_state` directly instead of calling `_enter`. Keep `_state` private, so only the class can change it, and only `_enter` writes to it.

**Names and states out of order.**
`state_names` must follow the order of `log_state`. Add a state to one and not the other, and the text is wrong or reads past the end of the array.

**It flickers between two states.**
Two transitions with the same condition, in opposite directions, fire one after the other. Here the log wakes within 48 and gives up past 96: the gap between them is what keeps it from switching every frame.
