## When to use it

When the game slows down, or before it does: when you add many objects, a big loop, or anything that runs every frame for every enemy. Measure first, because the slow part is rarely the one you'd guess.

## How to think about it

**Each frame has a budget.** The screen refreshes 60 times per second, so all of a frame's work has to fit in about 16.7 ms. `bn::core::last_cpu_usage()` says how much of the last frame was used: 1 is all of it. Past 1, the frame wasn't ready in time, the screen showed the old one again, and the game runs slower.

**First, watch the number.** Put the CPU usage on screen while you play. It tells you *when* it gets heavy, not *why*.

**Then, measure blocks.** `BN_PROFILER_START("name")` and `BN_PROFILER_STOP()` around a piece of code add its time to a table. `bn::profiler::show()` stops the game and shows that table, sorted by who took the longest.

**Then fix the biggest one, and measure again.** A fix that doesn't change the number wasn't a fix.

**It costs nothing when it's off.** The profiler only exists when the build has `BN_CFG_PROFILER_ENABLED`. Without it, the `BN_PROFILER_` lines turn into nothing, so you can leave them in the code.

`separate` takes 82% of the time. Its slowest run took 5748 ticks, and a frame has 4389 at Butano's default timer: that one block alone took longer than a whole frame.

### The fix

The reason is in the loop: it checks every pair of logs. Twice the logs means four times the pairs, which is why the bars curve up.

Logs don't need to be pushed apart every frame. With **SELECT**, each frame only checks a quarter of the logs against the others, taking turns, and pushes four times as hard. Every pair is still checked every 4 frames, and nobody can see the difference. With 64 logs, the CPU went from 132% to 56%.

Splitting a job across frames is a common fix. The others are doing less work, such as only checking nearby logs, or doing the same work faster.

## Pitfalls

**"'bn::profiler' has not been declared".**
The build doesn't have `BN_CFG_PROFILER_ENABLED`. The `BN_PROFILER_` lines compile to nothing without it, but a call to `bn::profiler::show()` doesn't. Add the flag to `USERFLAGS` in the Makefile, or remove the call.

**"There's already an active id".**
Blocks can't be nested, and every `START` needs its `STOP` before the next `START`. To measure a part of a block, give it its own `START` and `STOP` instead of nesting.

**Measuring once.**
One frame can be quiet and the next one heavy. Play for a while before **START**, so the table adds up many frames, and look at both views: total for what costs the most overall, max for what causes the spikes.

**Doing the heavy job every few frames.**
Running all of `separate` every fourth frame, instead of splitting it, makes three frames light and one as heavy as before. With 64 logs that one frame would still need more than a whole frame, going by the table above. Spread the work evenly.

**The meter changes the result.**
Writing text every frame costs time too. The snippet updates its numbers every 30 frames, and measures that in its own block to be sure.

**The emulator isn't the console.**
These numbers come from mGBA in a browser. Run on real hardware before trusting a number close to 100%.
