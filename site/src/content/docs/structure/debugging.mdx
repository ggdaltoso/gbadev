## When to use it

Whenever the game does something you didn't expect and you can't see why. The GBA has no debugger window next to the game and no `printf` to a terminal, so Butano gives you two tools: `BN_LOG` writes a line to the emulator's log, and `BN_ASSERT` stops the game with a message the moment something is wrong. Both come with every Butano project, already on.

## How to think about it

**`BN_LOG` writes to the emulator, not to the screen.** It takes any number of values, text, `int`, `bn::fixed`, `bool`, and writes them as one line to mGBA's log: in mGBA, **Tools → View logs**. Nothing appears in the game, so you can log without moving the HUD out of the way. In the snippet, every line below came from the emulator's log while the hero walked, stopped and was hit.

**`BN_ASSERT` stops the game where the bug is found, and says where.** `BN_ASSERT(condition, message...)` does nothing while the condition is true. When it's false, the game stops on Butano's error screen. The bug might have started far away, a caller asking for the wrong thing, but the game stops at the check instead of carrying on with a wrong number until something else breaks. Each line of the screen answers a question:

**The stack trace says how the game got there.** The error screen names the function the check is in, but not who called it. With `STACKTRACE := true` in the Makefile, Butano writes the chain of calls to the log after the error screen, innermost first. The names are as the compiler stores them: `_Z6damageii` is `damage(int, int)`, between `_Z` and the `i`s, `6damage` is the name and its length.

The flags go in `USERFLAGS` in the Makefile: `-DBN_CFG_LOG_ENABLED=false` and `-DBN_CFG_ASSERT_ENABLED=false`. Leave `STACKTRACE` empty to drop the stack trace. The stack trace alone took 41 KB, most of it probably the names of the functions (worked out, not measured), so it's the first thing to drop when the ROM gets big.

The page's emulator doesn't show the log. To see it, download [the ROM](/roms/debugging.gba) and open it in [mGBA](https://mgba.io/), then **Tools → View logs**. `BN_LOG` lines are at the warning level.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `BN_ASSERT(amount <= health, "Hit for ", amount, " with ", health, " health left");` | The condition first, then any number of values for the message, written like `BN_LOG`'s. The condition itself shows on the error screen too. |
| `[[gnu::noinline]] int damage(...)` | Asks the compiler not to paste `damage` into `main`. A function that small would be, and then it vanishes from the stack trace (see Pitfalls). |
| `if(was_walking && ! walking)` | Logs once, when the hero stops, instead of every frame it stands still. |
| `bool walking = step_x != 0 \|\| step_y != 0;` | One name for a condition used twice: in the `if` and to remember for the next frame. |
| `STACKTRACE := true` | Set before the `include`: `butano.mk` sets it with `?=`, only if nothing set it first. |

## Pitfalls

**With asserts off, the bug is still there, just quiet.**
A test ROM built with `-DBN_CFG_ASSERT_ENABLED=false` didn't stop at the fourth B. It took the health to -1, then -2 on the fifth, and showed "Health -2" as if nothing was wrong. Turning asserts off removes the check, not the bug. Butano doesn't even run the condition then: it tells the compiler to assume it's true (read in `bn_assert.h`).

**Work inside a `BN_ASSERT` disappears with it.**
A test ROM whose `damage` did the subtraction inside the check, `BN_ASSERT((health -= amount) >= 0, ...)`, worked while asserts were on. Built with them off, five hits left the health at 3: the log said "Hurt. Health: 3" five times. Put only questions in a `BN_ASSERT`, never changes.

**A log line has a size limit, and going over it is an error.**
A test ROM that logged 309 characters in one `BN_LOG` stopped before its first frame, on the error screen: "Not enough space: 309 - 255", from `bn_string.h`. A line is built in a buffer of `BN_CFG_LOG_MAX_SIZE`, 256 bytes by default. Log several short lines instead of one long one.

<figure style={{ textAlign: 'center' }}>

	<figcaption>One <code>BN_LOG</code> too long.</figcaption>
</figure>

**Logging every frame floods the log and costs CPU.**
Three test ROMs walked the hero right for 1.5 seconds and showed the CPU used per frame. With no log, 4.6% of the frame. With one `BN_LOG` of the hero's position every frame, 5.3%, and 173 lines in the log. With ten per frame, 12.2%, and 1721 lines, too many to read. A line cost about 0.7% of a frame. On a real GBA it's still built and written, just to an address nobody reads (worked out from Butano's `bn_hw_log.h`). Log when something changes.

**A small function can vanish from the stack trace.**
A test ROM without `[[gnu::noinline]]` stopped on the same error screen, still naming `damage` and line 20, because that comes from the check itself. But its stack trace was only `main`: the compiler had pasted `damage` into `main`, so at run time there was no call to list. When a trace looks too short, the missing functions were probably inlined.
