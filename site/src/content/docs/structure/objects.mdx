## When to use it

Enemies, bullets, coins, particles: anything that comes in numbers, each with its own position and state, appearing and disappearing while the game runs.

## How to think about it

**One class per kind of thing.** The class keeps what one of them needs: its sprite, its animation, what it's doing. `update()` runs one frame of it. Nothing outside needs to know how it works, only when to update it and when it's done.

**Many of them go in a `bn::vector`.** Its size is fixed when you write it, `bn::vector<log_enemy, 8>`, and the room for all 8 is reserved up front. Adding and removing never allocates memory, so it never fails halfway through a level, and there's no `new` or `delete` to forget. When it's full, it's full: decide what happens then.

**Each frame has the same three steps:** add what was born, update everything, remove what's done.

**A `bn::sprite_ptr` is a handle, not a sprite.** Copying it gives you a second handle to the *same* sprite. That's why a class can hold one and hand it to an animation, and also why copying an object by accident leads to strange bugs.

## The smallest thing that works

Logs come out of the corners, one per second, up to eight, and walk toward the hero. When one reaches them, it falls asleep for two seconds and disappears. Move with the **D-pad**.

A few pieces of C++ doing the work:

| In the code | What it does |
|---|---|
| `explicit log_enemy(...)` | A constructor that has to be called on purpose. Without `explicit`, a `bn::fixed_point` could turn into a log by itself where a log is expected. |
| `: _sprite(...), _animation(...)` | The initializer list, run in the order the members are declared. `_animation` needs `_sprite`, so `_sprite` comes first in the class. |
| `const bn::fixed_point&` | Reads the value without copying it, and promises not to change it. |
| `emplace_back(spawn_points[next_spawn])` | Builds the log inside the vector, with the constructor's arguments. No temporary log is made and copied. |
| `for(log_enemy& log : logs)` | `log` is each element itself, not a copy of it. |
| `[](const log_enemy& log) { return log.gone(); }` | A lambda: a small function written where it's used. `erase_if` calls it on every log and removes those that return `true`. |

## Pitfalls

**Objects move, but never change state.**
The loop is `for(log_enemy log : logs)`, with no `&`. Each log updates a copy of itself, and the copy is thrown away. The sprite still moves, because the copy's `sprite_ptr` is a handle to the same sprite, so it looks almost right: here the logs pile up on the hero and never fall asleep.

**Moving one object moves another.**
`bn::sprite_ptr twin = hero;` doesn't make a second sprite. `twin.set_x(50)` moves the hero. To get another sprite, call `create_sprite` again.

**"Vector is full".**
`emplace_back` on a full `bn::vector` stops the game with that message. Check `full()` first, as the snippet does, and decide what happens when there's no room: wait, as here, or replace the oldest.

**Removing objects inside the loop that updates them.**
Erasing from a vector moves the elements after it, so a range `for` that erases skips one and can run past the end. Update first, then remove with `bn::erase_if`.

**Too many sprites.**
The hardware shows 128 at once, and fewer on a single line before some vanish. Count the sprites each object uses, text included, when you pick the vector's size.
