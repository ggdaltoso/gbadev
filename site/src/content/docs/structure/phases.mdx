## When to use it

For a fight that should change as it goes: a boss that starts calm, gets angrier as its health drops, and ends in a last desperate burst. The player learns one set of attacks, then the rules change. The same structure fits a boss in any genre: a platformer boss that walks, then jumps, then throws things, or a shooter boss like the one here.

It builds on [Bullet patterns](/math/bullets/), for the attacks, and [State machines](/structure/states/): a phase is a state, picked by a number instead of by events.

## How to think about it

**Health picks the phase.** Each row of `phases` says the health a phase starts at: 200, 133 and 66. Every frame, `phase_for(health)` reads the table from the last row up and returns the first phase whose start the health has reached. The phase isn't something that happens, and nothing has to notice the moment health crosses a line: whatever the health is now, the phase follows from it.

**A phase is a list of attacks played in a loop.** An `attack` is a bullet pattern and how many frames it lasts. A phase points to its list with a `bn::span`, a view of a `constexpr` array that knows its length, so phases can have lists of different sizes. `attack_index` says which attack is playing, and `attack_frames` counts up to its length; then the index moves to the next one, back to the first after the last.

**A phase change is a fresh start.** When `phase_for` gives a different phase, the snippet starts the new list from its first attack, with its frame count at 0, clears the old bullets, and waits 60 frames before firing. All the counters belong to the list that was playing, so none of them mean anything in the new one. The clean screen also tells the player that something changed.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `bn::span<const attack> attacks;` | A pointer and a length together. `{ 133, angry }` makes one from the array `angry`, whatever its size. |
| `constexpr attack angry[] = { ... };` | Arrays built at compile time and kept in ROM, so the span points to data that lives as long as the game. |
| `attacks[attack_index]` | `bn::span`'s `[]` checks the index with `BN_ASSERT`, so an index past the end stops the game with a message instead of reading something else. |
| `bn::erase_if(shots, [&](bn::sprite_ptr& shot) { ... })` | The lambda moves each shot and says whether to remove it. `[&]` lets it change `health`. |
| `(attack_index + 1) % attacks.size()` | The next attack, and the first one again after the last. |

## Pitfalls

All three test ROMs got the same keys as the snippet: A held under the boss for the whole fight. The pictures are the same frame of each.

**A phase that waits for an exact health never starts.**
A test ROM that changed phase when `health == from_health` stayed in phase 1 for the whole fight, all the way to "Defeated". Each shot takes 3, so health went 134, 131, and never was 133; then 68, 65, and never 66. With a phase picked from a range, it doesn't matter which numbers health lands on.

**The last phase never comes.**
A test ROM that read the table from the first row down, returning the first phase whose start the health had reached, stayed in phase 2 below 66. Any health at or below 66 is also at or below 133, so the search stopped at phase 2 every time. Read from the last row up, the lowest phase reached wins.

**The new phase gets stuck on one attack.**
A test ROM that didn't reset `attack_index` and `attack_frames` on a phase change started phase 3 on its second attack, the fast fans, and fired them until the boss was defeated. The test was `== now.frames`, so the frame count carried over from phase 2 must have been past the 60 frames that attack lasts (worked out, not printed): counting up from there, it never equals 60. The turning rings of phase 3 never played.
