## When to use it

For a replay of the last run, a demo that plays on the title screen, a ghost to race against, or a bug that happens only after a certain sequence of moves. A replay keeps what the player pressed, which is tiny, instead of where everything was on every frame, which isn't.

For a bug you want to see again while developing, Butano already has a tool: the keypad logger (`BN_CFG_KEYPAD_LOG_ENABLED`) writes the buttons to the emulator's log, and `bn::core::init` takes them back to play them from the start. A replay inside the game, started from a menu or a key, is what this page builds.

## How to think about it

**A replay is the inputs, not what happened.** The game is the same code every frame: given where everything is and which buttons are held, it works out the next frame. Start it from the same place, with the same random seed, and give it the same buttons on the same frames, and it does the same thing. So a replay only needs the seed and the buttons. In the snippet, the last frame of the recording and the last frame of its replay were the same, pixel for pixel, except for the line of text at the top.

**The game reads its buttons from one place.** Every frame, the buttons the game uses are packed into one number, one bit each. `game::update` gets that number and never asks the keypad itself. While recording or playing, the number comes from the keypad; while replaying, it comes from the recording. The game can't tell the difference, and that's the point.

**Buttons change a few times a second, so store runs.** Held buttons stay the same for many frames in a row. Instead of one entry per frame, the recording keeps runs: these buttons, for this many frames. Measured in a test ROM with the same moves as the GIF below, a recording of 481 frames, about 8 seconds, was 15 runs. A run is two bytes, so that's 30 bytes, against 481 for one byte per frame.

## The smallest thing that works

Press **START** to record. Walk with the **D-pad**, hold **B** to run, and pick up coins. Press **START** again: the game starts over with the same seed and plays back what you did. When the replay ends, you have control again from where it ended.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `enum key_bits { up_bit = 1, ... };` | A plain `enum`, not `enum class`: its values are `int`s that combine with `\|` and test with `&`, like `keys & run_bit`. |
| `struct run { uint8_t keys; uint8_t frames; };` | Two bytes. `uint8_t` holds 0 to 255, which is why a run stops growing at 255 frames. |
| `bn::optional<game> current;` and `current.emplace(seed);` | The game is built in place inside the optional. `emplace` destroys the old game first, sprites included, then builds a new one: a fresh start with nothing left over. |
| `game` with members like `= bn::sprite_items::hero.create_sprite(0, 0)` | Default member initializers: every new `game` starts with the same values, so a start can't forget one. |
| `seed = frames * 2654435761u;` | A seed from when START was pressed, spread out so nearby frames give unrelated numbers. See [Timers and random numbers](/basics/timers/). |

## Pitfalls

**The coins are somewhere else.**
The random numbers are part of the start. In a test ROM where the replay got a new seed, the hero ran the same path and stopped at the same spot, but the coins were in other places: the recording took 3 coins and the replay 5. Keep the seed with the recording and start the replay with it.

**One button read straight from the keypad.**
A single `bn::keypad` call inside the game breaks the replay, because during a replay nobody holds that button. In a test ROM where running read `bn::keypad::b_held()` instead of the run bit, the replay walked where the recording had run, and ended at (54, -30) instead of (108, 2). Every button the game uses goes through `keys`.

**A run longer than its counter.**
A `uint8_t` counts up to 255 and then wraps to 0. In a test ROM without the `< 255` check, holding right for 5 seconds was recorded as 173 frames in all, when the base snippet recorded the same moves as 431. The replay walked right for much less time and ended at x -68 instead of 112. Start a new run when the count is full.
