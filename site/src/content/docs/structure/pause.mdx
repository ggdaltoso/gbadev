## When to use it

In almost every game. The player puts the GBA down to answer the door, and when they come back, nothing should have moved: the enemies, the hero's step, the clock. Meanwhile the pause menu itself has to work: a cursor that moves and blinks, a choice to resume or start again.

It's close to [Hitstop](/effects/hitstop/), which freezes the game for a few frames after a hit, and to [State machines](/structure/states/): paused and playing are two states of the whole game.

## How to think about it

**The loop never stops. Each frame runs either the game or the menu.** `bn::core::update()` still runs every frame, so the screen is still drawn and the keys still read. What changes is which code runs before it. START flips `paused`. Then one branch moves the logs, the hero and the clock, and the other moves the menu's cursor. Neither branch knows the other exists.

**What isn't updated stops, and nothing else does.** The logs' walk is a `bn::sprite_animate_action`, which moves to its next frame only when `update()` is called. The hero's step only changes in `walk.update()`. Both live in the game branch, so they stop mid-step. The cursor's blink counts `menu_frames`, which only the menu branch adds to, so it keeps blinking. Things Butano runs on its own keep going whatever the loop does: the music is the one in the snippet, so it gets `bn::music::pause()`.

**A timer that stays right counts the game's frames, not the loop's.** The clock is `time_left`, and the only `--time_left` is inside the game branch. While paused it isn't touched, so it waits at whatever it was. In the demo, the game was paused for about 3 seconds with the clock at 27, and it came back at 27. A timer worked out from a frame count that keeps running, like the loop's, would have lost those seconds (see the pitfalls).

## The smallest thing that works

The hero walks the arena with the **D-pad** while two logs wander and the clock counts down from 30. At 0 the round starts again. **START** pauses: the game goes dark and the music stops. **↑** and **↓** pick Resume or Restart, and **A** chooses. **START** again also resumes.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `bn::keypad::start_pressed()` | True only on the frame START goes down, so one press flips `paused` once, however long it's held. |
| `auto restart = [&]() { ... };` | A lambda that captures the locals by reference, so it can move the hero and refill `enemies`. It's called from the menu and when the clock runs out. |
| `bn::sprite_palette_ptr hero_palette = hero.palette();` | A copy of the handle to the hero's palette. `hero.palette()` gives a `const&`, which can't be faded. |
| `bn::bg_palettes::set_fade(bn::colors::black, fade);` | Mixes every background color with black: `0.6` is 60% of the way. |
| `bn::music::pause()`, `bn::music::resume()` | The music carries on from where it stopped. `bn::music::paused()` says which one is in effect. |
| `(time_left + 59) / 60` | Frames to seconds, rounded up, so the clock shows 1 until the last frame instead of 0 for a whole second. |

## Pitfalls

**A held START pauses and unpauses every frame.**
A test ROM that read `start_held()` instead of `start_pressed()` was held for about 36 frames: it was paused on every other frame, 18 in all, with the menu flickering. When the key came up it happened to be playing. An odd number of frames would have left it paused (worked out, not seen). Either way, the player can't tell what one press will do.

**A clock worked out from the loop's frames runs during the pause.**
A test ROM that kept a `frame` count, added to on every pass of the loop, and showed `deadline - frame` as the clock, was paused for 5 seconds. After resuming it showed 22, and the snippet, with the same keys, showed 28. Six seconds of the round were gone while nobody was playing. The same goes for a deadline from `bn::timer`, which counts the hardware's ticks no matter what the loop does (worked out from [Timers and random numbers](/basics/timers/), not tested).

**Darkening every sprite palette darkens the menu too.**
A test ROM that called `bn::sprite_palettes::set_fade` instead of fading the hero's and the logs' palettes dimmed the menu's letters and the clock with the rest. The text is still there, but grey on dark green. The letters are sprites like the hero, so a fade for all sprites can't skip them. Fading only the game's own palettes leaves the menu bright.
