## When to use it

When one cartridge holds several games: a party game made of minigames, a collection of arcade classics, the side games in an RPG (fishing, cards, a race), or a set of experiments that you want on one ROM. Each game has its own art and rules, and the player goes back to a menu between them. The records of all of them should survive turning the GBA off.

This page builds on [Scenes](/structure/scenes/), [Save slots](/basics/slots/) and [Level menu](/structure/levels/).

## How to think about it

**Each game is a scene that owns everything it creates.** A game is a function: it creates its background, sprites and text, plays until it ends, and returns the score. When it returns, every `bn::regular_bg_ptr` and `bn::sprite_ptr` it created goes out of scope and its graphics are freed, so the next scene starts from an empty screen, with all the sprites and VRAM free. The menu is a scene too. No game knows the others exist: Coin dash has a field and five coins, Dodge has a night sky and falling mines, and the menu only calls them through a table, `games[selected].play(text_generator)`.

**A game gives back a score, and only the hub touches the save.** There's one save for the whole ROM: one `save_data` at the start of SRAM, with a record for each game, and a format number and a checksum, as in [Save slots](/basics/slots/). The hub reads it once at start-up, and after a game it compares the score with that game's record and writes the save again only when the record is beaten. Games never read or write SRAM, so two of them can't write over each other, and a new game only needs a line in the table: `best` grows with it.

**A global setting belongs to no scene, so every scene that needs it sets it when it starts.** Some things aren't objects that go away with their scene. The backdrop color, the one the GBA shows where no background covers the screen, is one value for the whole console, and it stays until someone changes it. Dodge sets it to a night purple. Putting it back on the way out isn't reliable (see the pitfalls), so the menu sets its own blue every time it starts, whatever the last game left. The same goes for fades, blending, windows and the like: the scene that shows them sets them.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `int (*play)(bn::sprite_text_generator& text_generator);` | A pointer to a function that takes a text generator and returns an `int`. Every game has that shape, so one table holds them all. |
| `{ "Coin dash", coin_dash, " of 5" }` | A function's name, without `()`, is a pointer to it. |
| `games[selected].play(text_generator)` | Calls the function the pointer points to, like calling it by name. |
| `sizeof(games) / sizeof(games[0])` | The number of elements in a plain array, worked out by the compiler. It's `constexpr`, so it can size `best`. |
| `save = {};` | Every member set to 0: no records. |
| `bn::sram::read(save)`, `bn::sram::write(save)` | Read or write the whole struct at the start of SRAM. [Save slots](/basics/slots/) uses `read_offset` to keep several. |
| `bn::core::reset()` | Goes back to the start of `main()`, almost like turning the GBA off and on. SRAM keeps what was written: the menu shows the records again. |

## Pitfalls

**The menu stays on during the game.**
A test ROM that created the menu's panel and text in `main`, so they wouldn't have to be made again each time, kept them alive while the games ran. In Coin dash, the field, created later, hid the panel, but the menu's text stayed on top of the game. In Dodge, which has no background, the whole menu showed behind the mines. Create a scene's things inside the scene, so they go away with it.

**One game's save writes over another's.**
A test ROM where each game kept its own small save, a format, a record and a checksum, wrote all of them at the start of SRAM. Coin dash saved 5 coins, then Dodge saved 3 seconds at the same address. Before the reset the menu still showed both records, from RAM. After it, both games read Dodge's save, which was valid for each of them: Coin dash said "Best: 3 of 5", and the 5 was gone. Keep one save, with a place for every game, and let only the hub write it.

**The last game's color is left behind.**
A test ROM where the menu didn't set the backdrop came back from Dodge to a purple menu, though Dodge called `bn::backdrop::remove_color()` before returning. Removing it only forgets the color Butano was asked for. In Butano's source, the GBA's color 0 is written again only when a color is set or when the first background palette is copied again, and the purple stayed on screen, so neither happened here. The fix in the snippet is the menu setting its own color when it starts.
