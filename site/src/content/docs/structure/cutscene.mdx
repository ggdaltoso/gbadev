## When to use it

When the game takes over for a moment: a character talks, the camera goes to look at something, something happens, and then the player gets control back. Written as code, each new cutscene is another tangle of flags and timers. Written as a list of steps, a cutscene is data, and one small piece of code plays any list.

## How to think about it

**A cutscene is a list of steps, read top to bottom.** Each step is one thing: say a line, move the camera, wait, wake the log up. The list holds what to do and with what, like the text or the number of frames. The code that plays it only knows how to do each kind of step. Adding a line of dialog or a longer wait changes the list, not the code.

**One step at a time, and each step says when it's done.** The code keeps two numbers: which step is playing, and how many frames it has run. Every frame it runs that one step and asks if it's done. A say is done when A is pressed, a pan when the camera gets there, a wait after its frames. When a step is done, the number moves on, and the next step starts on the next frame. On its first frame a step sets itself up: the say shows its box then.

**Skipping plays what the steps leave behind, not the steps.** Pressing START mid-cutscene must leave the world as if the cutscene had played. So the skip goes through the steps that haven't run and applies only what each one leaves behind. In this script, only waking the log leaves something: text goes away when its box closes, waits leave nothing, and the camera follows the hero again as soon as the player has control.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `enum class action { say, pan_to_log, ... };` | The kinds of steps. `enum class` keeps the names inside `action::`, so `wait` can't clash with anything else called `wait`. |
| `{ action::wait, "", 60 }` | Aggregate initialization: the members in order. Leave the last ones out and they keep their defaults, so a say is just `{ action::say, "..." }`. |
| `constexpr auto script = bn::to_array<step>({ ... });` | The compiler counts the steps: `script.size()` is always right, and adding a step needs no other change. |
| `const step& now = script[current];` | A reference to the step in the script, not a copy of it. `const`, because playing a step never changes the script. |
| `auto wake_log = [&]() { ... };` | A lambda: a small function written inside `main` that uses its variables by reference. The step and the skip both call it, so they wake the log the same way. |
| `default: BN_ERROR("Unknown action");` | Stops the game with a message if a step's action has no case, like the [State machines](/structure/states/) page does. |

## Pitfalls

**One press closes two boxes.**
Playing the next step in the same frame saves a frame per step, but the frame's buttons are still the same. In a test ROM where a done step went straight into the next one, and a say read A on its first frame too, the A that closed "Who woke me up?" also closed "Go away. Let me sleep.", which never showed: the camera started back right away. Start the next step on the next frame, or read A only after the box's first frame. The snippet does both.

**A skip that just stops.**
Ending the cutscene on START without running what its steps leave behind skips their results too. In a test ROM with the skip only hiding the box, walking to the log after skipping found it still asleep and snoring, after a cutscene that was meant to wake it. Go through the steps left and apply what each one leaves.

**The cutscene plays again.**
The trigger is a place, and the hero is still standing there when the cutscene ends. In a test ROM without `played`, the first line, "Hero: Is someone snoring?", came back right after the last one closed. Remember that it played; in a game that saves, keep that in the save, like the [SRAM saves](/basics/saves/) page.

**A pan that never ends.**
A step that waits for an exact position must be able to reach it. In a test ROM where the camera moved an eighth of the way each frame, it slowed down near the log and the cutscene stayed there: after six seconds the log was still asleep, and the steps after the pan never ran. Move by at most a fixed step and clamp, as `pan` does, so the last step lands exactly. The [Interpolation and easing](/math/easing/) page has more on arriving exactly.
