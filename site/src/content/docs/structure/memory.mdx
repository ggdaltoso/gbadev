## When to use it

When the game grows: big tables, maps, buffers, or a function that has to run fast. The GBA has no memory manager and no operating system to warn you. Each variable lives in one of three places, picked when you write it, and getting it wrong costs speed, space, or a crash that shows up somewhere else.

## How to think about it

**Three places, each with its own size and speed.** IWRAM is small and fast, inside the CPU. EWRAM is eight times bigger and slower, on a separate chip. ROM is the cartridge: huge, but it can only be read. By default, code and `constexpr` data stay in ROM, and globals and the stack go in IWRAM. The snippet's screen shows how much of each it uses, with `bn::memory::used_static_iwram()` and friends: Butano itself already took 11080 bytes of IWRAM, a third of it.

**A global costs RAM and ROM; `constexpr` costs only ROM.** A global with a starting value needs that value somewhere when the GBA is switched off, so it's kept in ROM and copied to RAM when the game starts. A `constexpr` table is never copied: the code reads it straight from ROM. In a test ROM that made the snippet's `iwram_numbers` `constexpr`, IWRAM used dropped by exactly 8192 bytes, the array's size, and the ROM didn't change by a byte. Tables that never change, like levels, sine tables and enemy stats, should be `constexpr`.

**Where the code runs matters as much as where the data is.** The CPU fetches every instruction from wherever the code is, and code is in ROM unless you say otherwise. The snippet sums the same 2048 numbers from each place, with the loop in ROM and with the loop copied to IWRAM by `BN_CODE_IWRAM`. With the loop in ROM, the reads cost 14 to 19 cycles a number and the place of the data barely mattered. With the loop in IWRAM, IWRAM data took 8 cycles, ROM 9 and EWRAM 13.

**The stack grows down toward the globals.** Globals fill IWRAM from the bottom. The stack, where local variables live, starts at the top and grows down with every function call. Nothing stands between them. In the snippet, each call of `stack_at_depth` takes 264 bytes, its 256-byte buffer and a little more, and the screen shows what's left between the two.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `constexpr bn::array<int, count> make_numbers()` | A function the compiler runs while building the ROM, so the table is filled before the game starts. |
| `BN_DATA_EWRAM bn::array<int, count> ewram_numbers` | Moves a global from IWRAM to EWRAM. It still has a starting value, so it still takes ROM too. |
| `BN_CODE_IWRAM [[gnu::noipa]] int sum_with_iwram_code(...)` | Copies the function to IWRAM at boot. Worth it only for small, hot code: IWRAM is tiny. |
| `[[gnu::always_inline]] inline int sum(...)` | One loop pasted into both functions, so the only difference between them is where they live. |
| `[[gnu::noipa]]` | Stops the compiler from seeing which array is passed in and working the sum out while building, which would measure nothing. |
| `volatile char buffer[256];` | `volatile` makes the compiler keep the buffer on the stack even though it's barely used. |
| `bn::memory::used_stack_iwram()` | How far the stack has grown down from the top of IWRAM, right now. |

## Pitfalls

**A global too big for IWRAM doesn't build.**
A test ROM with one more global, `int grid[8192]`, 32 KB, failed to link: "section `.data' is not within region `iwram'". That's the good case: it fails before the game runs. Move big arrays to EWRAM with `BN_DATA_EWRAM`, or make them `constexpr` if they never change.

**A stack overflow doesn't crash: it overwrites the globals.**
A test ROM with a 16 KB local array in `main`, `volatile int scratch[4096]`, built and ran. Its stack took 17908 bytes, 4412 more than was free, and the IWRAM numbers summed wrong: the screen showed -1 where the cycles should be, because the stack had written over `iwram_numbers` (worked out from the wrong sum). Another test ROM let the chain of calls go to depth 70, 6500 bytes past the globals: no crash, and the screen looked fine, since nothing read the globals it had overwritten. Keep big arrays out of local variables, and watch `used_stack_iwram()` in deep or recursive code.

**Zeros in `BN_DATA_EWRAM` still take ROM.**
A test ROM with `BN_DATA_EWRAM int ewram_zeros[16384]`, 64 KB that start as zero, grew the ROM from 138344 to 203872 bytes: 64 KB of zeros stored to be copied. With `BN_DATA_EWRAM_BSS` instead, the ROM didn't grow (8 bytes smaller, from the code around it) and EWRAM grew by the same 64 KB: those are cleared when the game starts, not copied. Use `BN_DATA_EWRAM_BSS` for arrays without a starting value.

**With the code in ROM, timing the data says little.**
The first version of the snippet read EWRAM data in 14 cycles from ROM code, the same as IWRAM. After the code changed a little, the same read took 18. With the loop in IWRAM, every build measured 8, 13 and 9. Code in ROM waits on the cartridge for each instruction, so small changes in where it lands move the timings (worked out, not measured). Time hot code where it will run.
