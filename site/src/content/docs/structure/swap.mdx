## When to use it

When the player flips between two screens many times and each one should be exactly as it was left: a game and its inventory, a world and its map, a desk and a phone, two rooms of a puzzle. Nothing to load on the way, so the swap happens on the frame the button is pressed, and nothing to save and restore, because nothing was destroyed.

For screens that come one after the other and don't come back the same, a title, a level, a game over, use [Scenes](/structure/scenes/): each one owns its resources only while it runs.

## How to think about it

**Both screens are alive all the time; swapping only changes what's visible.** The field and the bag are two structs, each owning its background and its sprites, and `main` makes both before the loop. Pressing **SELECT** calls `set_visible(false)` on one and `set_visible(true)` on the other: every background and sprite it owns, hidden or shown. Nothing is created, nothing destroyed, so the hero's position, the cursor and the clock are simply still there.

**Hidden isn't paused: each screen decides what keeps going.** A hidden sprite still exists, and the code that moves it still runs if it's called. So the snippet decides, screen by screen. The field's `update` runs on every frame and counts the clock even while the bag is open, but it only reads the D-pad and redraws the clock when the field is shown. The bag's `update` only runs while the bag is shown, so the cursor can't move behind the player's back.

**Both screens share the hardware all the time.** Nothing is loaded when swapping because everything already is: both backgrounds, every sprite and their tiles and palettes sit in video memory together. That's the price. Here it's 2 of the 4 backgrounds and a handful of the 128 sprites, an easy fit; two big screens might not fit together, and then [Scenes](/structure/scenes/) is the way. The gain was measured: a test ROM showed the CPU time of the swap frame, next to a version that destroys one screen and makes the other on each swap.

Some of the C++ in the snippet:

| In the code | Why |
|---|---|
| `bn::regular_bg_ptr world = bn::regular_bg_items::world.create_bg(0, 0);` | A default member initializer: every `field_screen` starts with these values, without writing a constructor. |
| `::set_visible(clock, visible);` | Inside the struct, `set_visible` alone would mean the struct's own function. `::` asks for the one outside every struct. |
| `field_screen field;` and `bag_screen bag(text_generator);` | Made once, before the loop, so they live as long as `main`: that's what keeps their state. |
| `explicit bag_screen(bn::sprite_text_generator& text_generator)` | `explicit` stops a text generator from turning into a bag by accident where a bag is expected. |
| `(selected + 3 + down - up) % 3` | Wraps around: up from the first item goes to the last. The `+ 3` keeps the number positive, since `%` of a negative number is negative in C++. |

## Pitfalls

**Coming back to a screen that starts over.**
A test ROM that destroyed the field when opening the bag, and made a new one when closing it, as scenes do, brought the hero back to the middle of the screen and the clock back to 0:00. The swap still fit in its frame, at 1409 ticks of 4389 against 258 for the snippet, so the cost wasn't what showed: the lost state was. A screen meant to be the same when the player comes back has to stay alive.

**The hero walks while the bag is open.**
A test ROM whose field read the D-pad whether shown or not moved the hero while the player was in the bag. Holding **Down** for 42 frames to move the cursor, the hero, hidden, walked 42 pixels down; back on the field, it wasn't where it had been left. A hidden screen must not read the buttons.

**The clock shows up on the bag.**
A test ROM whose field redrew its clock every second, shown or not, put "Time 0:03" over the top of the bag. `set_visible(false)` had hidden the clock's sprites, but every redraw makes new ones, and new sprites are visible. The snippet only redraws the clock while the field is shown; coming back, the time changed, so it's redrawn on the first frame.
