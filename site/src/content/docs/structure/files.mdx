## When to use it

When `main.cpp` gets long enough that you scroll to find things, or when two files need the same class. Each kind of thing gets its own pair of files, and `main.cpp` goes back to just running the game.

## How to think about it

**Every `.cpp` is compiled on its own.** The compiler reads one `.cpp` at a time, from top to bottom, and knows nothing about the others. Each one becomes an object file, `.o`. Then the *linker* joins all of them into the ROM.

**A header is a promise.** `log_enemy.h` says that a class `log_enemy` exists, what's inside it, and which functions it has. That's enough for `main.cpp` to create logs and call `update()`, even without seeing how `update()` works.

**The `.cpp` keeps the promise.** `log_enemy.cpp` has the bodies of those functions, once, for the whole game. The linker connects each call in `main.o` to its body in `log_enemy.o`.

**`#include` pastes the file in.** It's a copy and paste, done before compiling. That's why a header can't be pasted twice in the same `.cpp`, and why it needs an include guard.

**You don't list the files anywhere.** Butano's build compiles every `.cpp` in the folders of `SOURCES`, and looks for headers in the folders of `INCLUDES`. By default those are `src` and `include`.

What goes where:

| In the header | In the `.cpp` |
|---|---|
| The class, with its members, so the compiler knows its size | The bodies of the functions, written as `log_enemy::update` |
| Includes for the members' and parameters' types | Includes only the bodies need, such as the sprite item |
| Short functions written inside the class, like `asleep()` | Everything else |

`main.cpp` doesn't include `bn_sprite_items_log.h` anymore. It doesn't need to know what a log looks like, only that logs exist.

A short function written inside the class is *inline*: it can be in the header, which is pasted into many files, without being defined twice. That's not true for functions outside a class, as the pitfalls show.

`log_enemy.cpp` includes its own header first. If the header ever forgets an include it needs, this is where it fails, instead of working by luck in a file that happened to include it earlier.

## Pitfalls

**"redefinition of 'class log_enemy'".**
The header was pasted twice into one `.cpp`, often through another header, and it has no include guard. Wrap it in `#ifndef`, `#define` and `#endif`, with a name no other header uses. `#pragma once` does the same in one line; Butano's own headers use guards.

**"multiple definition of `sleep_duration()'", from `ld`.**
A function outside the class has its body in the header. Every `.cpp` that includes it gets a copy, and the linker finds two. Move the body to the `.cpp` and leave only `int sleep_duration();` in the header, or mark it `inline`.

**"undefined reference to `log_enemy::update(...)'".**
The linker found the promise but not the body. Either the function isn't defined in any `.cpp`, its name or parameters differ from the header, or the `.cpp` isn't being compiled at all. A `.cpp` in a subfolder, like `src/enemies/`, is ignored until you add that folder to `SOURCES` in the Makefile.

**Two files with the same name in different folders.**
`src/log_enemy.cpp` and `src/enemies/log_enemy.cpp` both become `log_enemy.o`, and one replaces the other. You get "undefined reference" for functions that are clearly there. Give every `.cpp` a different name.

**"'log_enemy' was not declared in this scope".**
The file uses the class but doesn't include its header. Each `.cpp` needs its own `#include`: the compiler doesn't remember what another file included.
